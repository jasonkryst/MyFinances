# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

MyFinances is a privacy-first, client-side-only personal finance tracker (debt payoff planning, accounts, income, budgets, savings, net worth, cash flow forecasting). It is **vanilla ES6+ JavaScript with no build step, no framework, and no backend** — all data lives in browser `localStorage`. The only external dependency is Chart.js, loaded via CDN.

## Commands

### Run the app locally
```bash
python -m http.server 32900
# or
docker compose up -d   # http://localhost:32900
```
Tests assume the app is being served at `http://localhost:32900/` (see `tests/conftest.py` `BASE_URL`) — start the server before running Playwright-based tests.

**Port conflict / Docker:** Docker's port binding on 32900 persists even through `docker compose pause`. If Docker owns the port, either run `docker compose stop` first, or start a server on another port and set `TEST_BASE_URL`:
```bash
python -m http.server 32901
TEST_BASE_URL=http://localhost:32901/ pytest tests/ -v
```

**Login gate:** When the Docker stack is running, `checkPostgresBackendPresent()` detects the `X-Myfinances-Backend: postgres` header on `HEAD /` and shows a full-page login gate that blocks all tests. The `app_page` fixture in `tests/conftest.py` intercepts that request and strips the header automatically — no manual action needed for tests using `app_page`. To clear any persisted Postgres backend preference left by a prior run, add this before navigating:
```js
localStorage.removeItem('debtTrackerStorageBackend');
```

### Tests
```bash
pip install playwright pytest pytest-asyncio
playwright install chromium

pytest tests/ -v                  # all tests
pytest tests/security/ -v         # XSS, CSP, input validation, static scan
pytest tests/features/ -v         # per-feature CRUD/business logic tests
pytest tests/ui/ -v                # mobile, modals, dark mode, accessibility
pytest tests/integration/ -v       # end-to-end workflows / smoke tests
pytest -m "not slow" -v             # skip slow tests

# Single file / single test
pytest tests/features/test_debts.py -v
pytest tests/features/test_debts.py::test_add_debt -v
```
`pytest.ini` sets `asyncio_mode = auto`. Custom markers (`security`, `feature`, `ui`, `integration`, `slow`) are registered in `tests/conftest.py`.

### Server tests
```bash
cd server
docker compose -f docker-compose.test.yml up -d   # Postgres on :5433
export DATABASE_URL="postgres://myfinances_test:myfinances_test@localhost:5433/myfinances_test"
npm run migrate up && npm test                   # node:test, server/test/*.test.js
```
Runs in CI as the `test-server` job against a `postgres:16-alpine` service container (issue #407 — before that, nothing ran this suite).

**App readiness in tests (issue #422):** `src/app.js` sets `<html data-app-ready="true">` once `new DebtTrackerApp()` and `init()` settle, even if startup fails. The `app_page` fixture waits for that marker after `goto`, and wraps `page.reload()` so every reload waits too. For a raw `page` fixture, or for a `goto`, call `tests.conftest.wait_for_app_ready(page)`.

**Lazy pages render asynchronously.** `switchPage('reconcile'|'reports')` returns before the lazy-loaded module renders. Reading the DOM straight away only used to pass because of the startup race. Seed inside `async () => { …; app.switchPage('reconcile'); await app.renderReconciliationPage(); }` (or `await app.renderReportsPage()`), or wait for a selector. `applyReconciliation` also awaits its module before showing `#alertModal`, so wait for `#alertModalOkBtn` to be visible first.

### Mutation testing
```bash
npm install
npm run test:unit       # Jest unit tests — tests/unit/*.test.js
npm run test:mutation    # Stryker — mutates the tested functions in src/debtCalculator.js, src/utils.js, src/sanitizers.js and re-runs the Jest suite per mutant
```
This is a separate, dev-only toolchain from the Python/Playwright suite above — Node/Jest/Stryker are never shipped to the browser (`index.html` is unaffected). `stryker.config.mjs`'s `mutate` array uses line-range globs scoped to exactly the functions covered by `tests/unit/*.test.js` (not whole files) — the pure, DOM-free `calculatePaymentPlan`/`formatDate`/`calculateMonthsBetweenDates` in `debtCalculator.js`, most of `utils.js`'s formatting/sanitizing helpers, and the record-shape sanitizers in `sanitizers.js` that don't need `app`/DOM state. Feature modules taking `app`/DOM state are out of scope. See `docs/superpowers/specs/2026-08-02-stryker-js-mutation-testing-design.md`.

## Architecture

### No build step — two script-loading modes
`index.html` loads scripts in a specific order that matters:
```html
<script src="src/debtCalculator.js"></script>           <!-- classic script, global DebtCalculator -->
<script src="...chart.umd.min.js"></script>             <!-- Chart.js from CDN -->
<script type="module" src="src/app.js"></script>        <!-- ES module entry point -->
```
`debtCalculator.js` is the only non-module file (pure, side-effect-free calculation engine) and is exposed as a global. Everything else is an ES module imported from `src/app.js`.

### Central app object + feature-module delegation pattern
`src/app.js` defines `DebtTrackerApp`, instantiated once as `window.app` on `DOMContentLoaded`. It holds **all application state** (`this.debts`, `this.accounts`, `this.incomes`, `this.bills`, `this.expenses`, `this.recurringTemplates`, `this.emergencyFunds`, `this.sinkingFunds`, `this.monthlySnapshots`, `this.reconciliations`, `this.ledgerAmountOverrides`, etc.) plus UI state (`editingDebtId`, `liabilitiesSubTab`, `_reportMonthOffset`, `_forecastRangeMonths`, ...).

Every feature module (`debts.js`, `debtBreakEven.js`, `breakEven.js`, `accounts.js`, `income.js`, `bonusAdvisor.js`, `bills.js`, `recurring.js`, `savings.js`, `reports.js`, `reportsNetWorth.js`, `reportsCalendar.js`, `reportsCashFlow.js`, `reportsMoneyFlowSankey.js`, `reportsVariance.js`, `reportsSummary.js`, `forecast.js`, `health.js`, `spending.js`, `ledger.js`, `ledgerTransactions.js`, `ledgerOverrides.js`, `ledgerCleared.js`, `reconciliation.js`, `strategy.js`, `strategyPlanCalculation.js`, `strategyCalendar.js`, `strategyComparison.js`, `strategySummaryTable.js`, `strategyScheduleTable.js`, `charts.js`, `ui.js`, `storage.js`, `storageAdapters.js`, `sanitizers.js`, `dataExport.js`, `dataTransferModal.js`, `commandPalette.js`, `keyboardShortcuts.js`, `settings.js`, `setupWizard.js`, `loginGate.js`, `serviceWorker.js`, `i18n.js`, `utils.js`, `postgresSync.js`, `postgresImport.js`, `pgMigrationModal.js`, `guideNav.js`, `guideTheme.js`) exports plain functions that take the app instance as their **first argument** (e.g. `addDebt(app)`, `computeAccountBalance(app, accountId, year, month)`). `DebtTrackerApp` methods are thin wrappers that call these functions with `this`. When adding a feature, follow this same pattern — put logic in a module function `featureFn(app, ...)` and add a one-line delegating method on `DebtTrackerApp`.

### Module import constraints

`ui.js` and `postgresSync.js` participate in circular ES-module import cycles with domain feature modules (example: `postgresSync.js → ui.js → ledger.js → settings.js → postgresSync.js`). These cycles are safe **only** because every involved export is a hoisted `function` declaration — ESM resolves hoisted functions across cycles without a TDZ issue. **Never convert an export in `ui.js` or `postgresSync.js` from a `function` declaration to an arrow-function `const`** without first auditing all callers for cycle membership. An arrow-function `const` export that is read during module evaluation of a sibling in the cycle will throw a ReferenceError (TDZ crash) at startup.

`src/people.js` adds a new leg to this cycle: `ui.js → people.js → postgresSync.js → ui.js` (verified safe 2026-10-19). `people.js` imports `pgPost`, `pgPatch`, `pgDelete` from `postgresSync.js` and `showDeleteConfirmModal`, `showAlertModal`, `showPersonReplacementModal` from `ui.js`; `ui.js` imports `refreshPersonSelectors` from `people.js`. All eight `people.js` exports (`buildPersonOptionsHtml`, `refreshPersonSelectors`, `renderPeopleList`, `addPerson`, `deletePerson`, `startEditPerson`, `cancelEditPerson`, `saveEditPerson`) are hoisted `function` declarations — none are arrow-function `const` exports — so the cycle is safe.

### Page navigation
Top-level pages (`data-page` buttons in `index.html`): `health`, `accounts`, `income`, `liabilities` (Debts + Budget sub-tabs), `recurring`, `savings`, `strategy` (Plan), `reports`, `ledger`, `reconcile`. `switchPage(app, pageName)` in `src/ui.js` shows/hides page sections, records `app._currentPage`, and calls `renderPageData(app, pageName)` — the per-page `render*` dispatch — when adding a new page, register it there. `renderPageData` takes a `{ resetToDefaults }` option (default `true`) guarding view-state resets that should only happen when navigating into a page (Liabilities defaulting to its Debts subtab, Reports zeroing its month offset); `app.refreshCurrentPageData()` calls it with `resetToDefaults: false` to re-render the currently visible page in place after data changes underneath it (e.g. a JSON import) without disturbing the user's current view.

### Storage & data flow
- `storage.js` persists app state under key `debtTrackerData` through a storage-adapter abstraction (`src/storageAdapters.js`), and is now scoped to save/load/quota/clear — sanitization lives in `sanitizers.js` and JSON export/import (current format version `"3.0"`) plus CSV export live in `dataExport.js`.
- **Storage adapters**: `app.storageAdapter` is either a `LocalStorageAdapter` (default) or `SessionStorageAdapter`, chosen at startup from `getStorageBackendPreference()` — a dedicated `debtTrackerStorageBackend` key always read/written directly against `localStorage` (never through the adapter, since it decides which adapter to build). Users switch backends from the Settings modal, which calls `app.switchStorageBackend(kind)`; this migrates current data into the new backend and removes it from the old one. The adapter interface (`get`/`set`/`remove`) is deliberately synchronous to match `localStorage`/`sessionStorage`; a future async backend (IndexedDB, a remote API) would require promoting the interface to Promises and updating every `saveToStorage()`/`loadFromStorage()` call site — see `docs/superpowers/specs/2026-07-14-storage-abstraction-design.md`.
- Every record type has a `sanitizeX()` function in `sanitizers.js` (e.g. `sanitizeAccount`, `sanitizeDebt`, `sanitizeIncome`, `sanitizeBill`, `sanitizeExpense`, `sanitizeLedgerOverrides`) that runs on **both load and import**, using the shared sanitizers from `utils.js` (`normalizeText`, `sanitizeFiniteNumber`, `sanitizeInteger`, `sanitizeDateISO`). New persisted fields must get a sanitizer entry or they won't survive export/import round-trips.
- **Import warning collection (issue #291)** — `sanitizeParsedState(parsed, warnings)` takes an optional second `warnings` array; when passed, it's populated with one entry per coerced field (`{recordType, recordName, kind: 'coerced', field, from, to}`) and one per record/entry dropped entirely (`{recordType, recordName, kind: 'rejected', reason}`), across every importable collection including the `ledgerAmountOverrides`/`ledgerClearedTransactions` maps and the post-merge balance-history orphan filter. Omitting `warnings` (the normal load-from-storage and Postgres-migration call sites in `storage.js`/`pgMigrationModal.js`) costs nothing extra and behaves exactly as before — only `dataExport.js`'s `importAllJSON` opts in. `dataTransferModal.js`'s `showImportResult(kind, message, warnings)` renders these as a collapsible `<details>` list (built with `createElement`/`textContent`, never `innerHTML` of the warning text) inside the Backup & Restore modal; a malformed-JSON hard failure stays in the same inline error banner (never a popup `alert()`-style modal, per the modal's established no-native-dialogs pattern — see `tests/ui/test_data_transfer_modal.py`) but now includes the native `JSON.parse` error message. When adding a new array collection to `sanitizeParsedState`, use the existing `_sanitizeRecordArray`/`_sanitizeValueArray` helpers rather than a bare `.map().filter()`, or it silently won't participate in warning collection.
- Import enforces a 2 MB max file size and supports legacy v1.0 (debts-only) files.
- `saveToStorage()` estimates the serialized payload size against a conservative 5MB quota on every save and calls `app.showStorageQuotaWarning()` (defined in `ui.js`) once usage crosses ~80%, or on an actual `setItem` failure.
- `utils.js` also hosts shared formatting/date/number helpers (`formatShortDate`, `formatMonthYear`, `dateToISO`, `parseFiniteOrNull`, `getReportDate`, `countIncomePaydaysInMonth`, `dailyCompoundInterest`) — check there before adding a new local date/number formatter in a feature module.

### Versioning
`APP_VERSION` (`src/utils.js`) is a hand-maintained semver string shown in the app footer — there's no `package.json`/build step to derive it from, so it's the single source of truth for the running app's version. Every bump must land alongside a matching `## [x.y.z] — YYYY-MM-DD` entry at the top of `CHANGELOG.md`; `tests/features/test_versioning.py` enforces that the two stay in sync (and that changelog headings stay in descending order), since nothing else previously caught a version-only commit with no changelog entry (see #59). Every **minor** bump (`x.Y.0`) also needs a user-facing entry at the top of `WHATS_NEW_ENTRIES` in `src/ui.js` (the account menu's What's New modal; patch releases don't need one), and `sw.js`'s `CACHE_NAME` must match too (`tests/features/test_pwa.py`). `tests/features/test_whats_new.py` enforces What's New: newest entry's major.minor must equal `APP_VERSION`'s, and no CHANGELOG minor release may be missing — it drifted 6.41→6.48 unnoticed because that test file wasn't in any `ci.yml` shard. **Feature/UI CI shards list test files explicitly — a new `tests/features/`/`tests/ui/` file must be added to a shard in `.github/workflows/ci.yml` or it never runs in CI.** `tests/features/test_ci_shard_coverage.py` (issue #415, shard K) now fails CI when a file is missing from every shard, listed twice, or a shard references a deleted file — it was added after 16 files were found never to have run, 5 of them with rotted failures.

### Calculation engine
`src/debtCalculator.js` (`DebtCalculator`, global) is a pure, side-effect-free engine for payoff schedules — daily-compounding interest, four strategies (Avalanche, Snowball, Priority-Lowest, Priority-Highest), per-month stimulus, and a binary-search back-calculator for target payoff dates. Keep it free of DOM/state access; all rendering happens in `strategy.js`.

### Cross-cutting features
- **Bills** (`bills.js`) — the standalone Bills UI (`#billForm`/`#billList`) was intentionally removed 2026-05-29 in favor of Recurring Templates (`recurring.js`), and there is currently no reachable UI to add or edit a bill. `bills.js` still defines the full data model, sanitizer, and calculation logic, and `app.bills` remains a live data dependency read by `accounts.js`, `health.js`, `ledger.js`, and `strategy.js` — existing bills data (from an older export, or injected directly into app state) still round-trips through storage/import/export and flows through every calculation correctly. See `tests/features/test_bills.py`'s `test_no_reachable_bill_add_ui`, which documents this gap as intentional rather than a regression.
- **Accounts** (`accounts.js`) are the hub: income, debts, bills, expenses, bonuses, and recurring templates can all link to an `accountId`, and `computeAccountBalance()` projects an account's end-of-month balance from all linked items.
- **Ledger** (`ledger.js`) aggregates income, debts, bills, expenses, and recurring templates into a unified transaction list, with a modal-based amount-override system (`ledgerAmountOverrides`, keyed `type|id|accountId|date`) and a per-transaction Cleared checkbox (`ledgerCleared.js`, `app.ledgerClearedTransactions`, keyed the same way) that records whether/when a transaction actually posted — informational only, it does not affect running balances.
- **Reports/Forecast/Health** (`reports.js`, `forecast.js`, `health.js`) all derive from the same underlying account/income/debt/recurring data — when changing a data shape, check all three for consumers.
- **Net worth projection** (issue #335) — `computeNetWorthProjection(app, horizonMonths)` in `reportsNetWorth.js` grows assets by `monthlyIncome - nonDebtExpenses - cashPaidToDebtThisMonth` each month and sources liabilities from `app.lastPaymentPlan`'s real per-debt `balance`/`payment` schedule when one exists (debt principal is a dollar-for-dollar asset→liability transfer, not a net-worth change — only the cash actually paid and true expenses move it). Falls back to a flat `(income - expenses)` delta per month, no debt compounding, once a plan ends or none exists. The Net Worth report's trend chart renders this as a dashed continuation of the historical Net Worth line (two datasets sharing one label axis, the projected one null everywhere except the single point where it should visually connect) — selectable 1/3/5-year horizon (`app._netWorthProjectionYears`), independent of the existing 3/6/12-month history-range buttons (`app._netWorthRangeMonths`).
- **Spending year-over-year toggle** (issue #332) — `renderReportsSpending` (`spending.js`) supports a `app._spendingYoYMode` toggle swapping each category badge's baseline from the prior calendar month to the same month one year prior; `computeSpendingByCategory(app, year, month)` itself is unchanged (still always computes its own internal prior-month delta) — the YoY baseline is a separate `computeSpendingByCategory(app, year - 1, month)` call compared via a local `_totalsByCategory`/`_changeVsBaseline` helper pair, so a category with no prior-year data simply shows no badge instead of a misleading 0%.
- **Income Trend chart** (issue #262) — `renderIncomeTrendChart(app)` in `income.js` renders a trailing 12/24-month stacked bar (Regular Income vs. Bonuses, via `countIncomePaydaysInMonth`/`computeMonthlyBonusesForMonth`) with an optional dashed year-over-year overlay line; hidden via the `#incomeTrendCard` `hidden` class when there's no income or bonus data. Called from `renderIncomeList`/`renderBonusList` themselves (not a separate `renderPageData` dispatch entry) so it stays in sync with every add/edit/delete mutation on either list.
- **Income gross vs. net modeling** (issue #251) — income records gain an optional `withholdingPercent` field (0–99.9, default `0`, so an unset field is a no-op), sanitized in `sanitizeIncome()` and surviving export/import. `computeNetIncomeAmount(income)` (`src/utils.js`) derives take-home pay as `amount * (1 - withholdingPercent/100)`; `computeMonthlyIncomeForMonth()` now returns **net** (it's the single function every cash-flow call site — Health's DTI/savings/cash-flow card, Cash Flow summary, the Debt-to-Income chart, Home Purchase affordability, the Net Worth projection, Plan's suggested-payment/income widgets — already called, so withholding only needed to be applied once, there). `ledgerTransactions.js`'s generated income transactions also post the net amount, so everything downstream of the ledger stream (Account projections, Forecast, and the Cash Flow/Money Flow/Variance/Summary reports) inherits net automatically. The raw `amount` stays **gross** and is still what's edited in the Add/Edit Income forms and shown in the payoff/report calendars' per-event tooltips (which show every event type's raw entered amount, not just income's). Income cards show net as the primary amount with a gross tooltip/secondary line when withholding is set. Health's DTI card notes which basis (`health.dtiBasisNet`/`health.dtiBasisGross`) is active. Wired to the optional Postgres backend via migration `1755600000022_add-withholding-percent-to-incomes.js` (`withholding_percent numeric NOT NULL DEFAULT 0`) and `/api/incomes`'s `columns` map — no sanitizer change needed server-side since `server/src/sanitizers/index.js` re-exports the frontend `sanitizeIncome()` by relative path.
- **Command palette** (`commandPalette.js`) — Ctrl/Cmd+K or the toolbar `#commandPaletteBtn` opens a searchable jump list across all pages plus common actions; initialized once from `ui.js`'s `initializeEventListeners()`. New pages should be added to its command list alongside `switchPage()`'s page-name mapping.
- **Keyboard shortcuts panel** (`keyboardShortcuts.js`) — `#keyboardShortcutsModal` is rendered entirely from the `KEYBOARD_SHORTCUTS` constant (opened via the command palette's "Keyboard shortcuts" command or the account menu's `#accountMenuShortcutsBtn`, delegating to `app.openKeyboardShortcuts()`). **When you wire a new `keydown` shortcut anywhere, add/update its entry in `KEYBOARD_SHORTCUTS`** — `tests/ui/test_keyboard_shortcuts.py` asserts the panel's rows match the constant 1:1.
- **Settings modal tabs** (issue #322) — `#settingsModal` (markup in `index.html`, wiring in `setupWizard.js`'s `initSettingsModal`) is split into four `data-settings-tab` panels (Appearance, Data & Storage, Notifications, Advanced), mirroring the Data Transfer modal's `data-dt-tab` pattern under its own `settings-tab-*`/`settings-tab-panel` class namespace so the two stay decoupled. The active tab is an in-memory variable scoped to `initSettingsModal` (not persisted), restored on each `open()`; the modal's auto-focus-on-open targets the first focusable control inside whichever tab is active rather than a fixed element, so adding a setting to a given tab doesn't require touching the focus logic. Moving an existing control to a different tab means it's no longer visible/focusable without first clicking that tab — update any Playwright test that drives it directly.
- **Health per-card credit utilization breakdown** (issue #281) — the Credit Utilization card's toggle (`renderCardUtilBreakdownHtml` in `health.js`) renders one row per `debtType: 'creditCard'` debt (not just ones with a limit set), including a `.health-card-util-name` span holding the debt's raw name. Health renders on every app load (it's the default landing page), and like every other page its markup stays in the DOM — just class-hidden — after navigating away, so an unscoped Playwright `text=<name>` locator elsewhere in the app can match this hidden span instead of the element a test actually means, and then time out waiting for it to become visible. Any test that creates a credit-card debt and later does `wait_for_selector('text=<that name>')` off the Health page must scope the locator to the page's own container (e.g. `#debtsList >> text=...` on Liabilities) — this bit `tests/postgres/test_postgres_mutations.py`'s `test_debt_delete_persists`/`test_debt_edit_form_renders` in CI (not reproducible locally without the docker-compose Postgres stack).
- **Ledger category filter + Spending cross-navigation** (issue #315) — `app._ledgerCategoryFilter` (default `'all'`) filters `getFilteredSortedLedgerTransactions` (`ledgerTransactions.js`) the same way the existing account/date/cleared filters do, persisted via the same `debtTrackerLedgerFilters` localStorage blob. The Spending report's category drill-down modal (`spending.js`'s `_openSpendingDrilldown`) has a "View in Ledger →" link that sets this filter plus `app._ledgerCrossNavLabel` (a breadcrumb string) and calls `switchPage(app, 'ledger')`; `switchPage()` (`ui.js`) clears `_ledgerCrossNavLabel` whenever navigating to any page other than `'ledger'`, so the breadcrumb only shows for the single visit it was set for.
- **Reconciliation statement range** (`reconciliation.js`) — reconciliations record `statementStartDate`/`statementEndDate` (issue #275); `date` mirrors the end date and is what Ledger/History position the entry by. `getDefaultStatementRange(app, accountId)` (day after the last reconciliation → today) and `validateStatementRange(start, end)` are shared by the Reconcile page cards and `#reconcileModal`. Legacy records have both fields `null`.
- **Chart accessibility** — every Chart.js canvas should have a `renderChartDataTable(canvasId, { caption, columns, rows })` call (from `utils.js`) immediately after construction, so screen-reader users get an equivalent `.sr-only` `<table>`. New chart-rendering code should follow this pattern.
- **Control labelling (issue #331)** — every `button`/`[role=button]`/`[role=tab]` needs an accessible name (visible text, `aria-label`, or `aria-labelledby`); `tests/ui/test_aria_labels.py` scans every page for violations. Text buttons keep their visible text and need no `aria-label`, **except** per-item actions rendered in a list (Edit/Delete/Save/Cancel/Pause/etc.), whose `aria-label` must start with the visible word and name the item (`Delete ${escapeHtml(item.name)}`, `Save changes to …`, `Cancel editing …`) — always `escapeHtml()` the name since it lands in an attribute. Toggle-style buttons (range chips, sub-tab buttons, show/hide archived) must carry an explicit `aria-pressed="true|false"` kept in sync in the same render/handler that flips the `active` class (never omit it for the off state). Clickable `<th>` sort headers need `tabindex="0"`, Enter/Space handling, `aria-sort` on the active column, and an `aria-label` like `Sort by Amount, descending`. Real tab widgets use `role="tab"` + `aria-selected` instead of `aria-pressed`.
- **Responsive tables/grids** — wide data tables/grids come in two flavors, and picking the wrong one on a narrow-column layout causes silent content clipping (not an ugly-but-visible overflow) whenever the container also has `overflow: hidden` for rounded corners. (1) Genuinely wide multi-column data (Net Worth History, Cash Flow Forecast, Ledger, Strategy schedule, comparison tables): wrap in a `.table-wrapper`/`-wrap` class (`overflow-x: auto`) so it scrolls horizontally — see `ledger-table`, `comparison-table`, `nw-history-table` (non-`--compact`), `recon-table-wrap`. (2) Few-column summary rows meant to be read top-to-bottom on mobile (Debt Overview categories, Account Balances/Money Flow, Budget Variance, Summary Report tables): below the mobile breakpoint, hide the header row and restack each row into a single-column label/value card via `content: attr(data-label)` on a `::before` — see `.nw-history-table--compact`, `.var-row`/`.var-header`, `.debt-overview-cat-row`, `.acct-mf-row`. Never leave a summary grid on fixed-px `grid-template-columns` with no mobile treatment — that's what caused the clipping bug fixed in 4.19.0.
- **Reduced motion** — `app.js` disables `Chart.defaults.animation` at startup when `prefers-reduced-motion: reduce` is set; `styles.css` has a matching global media query for CSS transitions/animations. New animated CSS should rely on the existing global rule rather than adding a bespoke override.
- **Internationalization** — `src/i18n.js` provides `t(key, vars)` string lookup (falls back to English, then to the raw key, so a missing/mistyped key never crashes or renders blank), `getCurrentLocale()`/`getIntlLocale()`, and `applyStaticTranslations()` which walks `[data-i18n]` (textContent) and `[data-i18n-attr]` (comma-separated `attr:key` pairs, e.g. `"title:toolbar.settingsTitle,aria-label:toolbar.settingsAriaLabel"`) elements and sets translated text via `textContent`/`setAttribute` — never `innerHTML`, so the CSP is unaffected. Locale dictionaries live in `src/locales/{en,es,pl}.js` as flat dot-keyed string maps; `en.js` is canonical, `es.js`/`pl.js` only need pilot-scope keys. The locale preference is stored directly under `debtTrackerLocale` in `localStorage` (same pattern as `debtTrackerTheme`/`debtTrackerStorageBackend` — a device preference, not app data). Only nav, the toolbar, the Settings modal, and the Health page (`health.js`) are translated so far; other pages remain English pending follow-up issues. `formatCurrency`/`formatShortDate`/`formatMonthYear` in `utils.js` read `getIntlLocale()` instead of a hardcoded `'en-US'`, so number/date formatting conventions follow the active locale app-wide with no call-site changes. See `docs/superpowers/specs/2026-08-04-i18n-support-design.md`.

Retrofitting the same `⇄` indicator onto the existing recurring-transfer type's ledger rows (currently plain `type: 'recurring'`) is tracked separately as **issue #399**, since it touches already-shipped behavior.

- **$0 amount policy** (issue #412) — `zeroAmountPolicy` setting (`ZERO_AMOUNT_POLICY`/`getZeroAmountPolicy(app)` in `settings.js`; `'allow'` default | `'warn'` | `'block'`, unknown stored values fall back to allow) selected in Settings → Advanced. `confirmZeroAmountAllowed(app, label)` (hoisted function in `ui.js`, reusing `showDeleteConfirmModal`/`showAlertModal`; `ui.js` now imports `settings.js`, safe because `settings.js` only has function/const-string exports read at call time) is the single gate, called by the Ledger override modal confirm (`ledgerOverrides.js`) and recurring add/inline-edit (`recurring.js` `validateRecurringAmount`). Blank/whitespace amounts and negatives are always rejected regardless of policy. Transfers keep requiring > 0: one-off transfers (`transfers.js`) are unchanged and `type: 'transfer'` recurring templates reject $0 before the policy is consulted. The setting rides the generic `app.settings` store (Postgres via `pgPut`, export/import already handled).

- **Lazy-loaded (dynamically imported) feature modules (issue #278)** — `src/app.js` statically imports most feature modules, but `src/retirement.js` (+ `retirementCalculator.js`), `src/reconciliation.js`, `src/strategyCalendar.js` (the Plan page's Calendar sub-tab), and the five Reports sub-tab modules (`reportsCalendar.js`, `reportsMoneyFlowSankey.js`, `reportsCashFlow.js`, `reportsVariance.js`, `reportsSummary.js`) are loaded on demand via `src/lazyModules.js`'s `loadRetirementModule()`/`loadReconciliationModule()`/`loadStrategyCalendarModule()`/`loadReportsSubModules()` — each wraps native ES module `import()` in a cache keyed by module name, so a module is fetched **at most once** no matter how many times its page is visited; a failed load is *not* cached, so a later retry re-fetches instead of being stuck. Every `app.js` wrapper method for one of these modules is `async` and `await`s the loader itself (not just the "entry point" render methods) — existing data-layer tests call these directly without first navigating to the owning page, so none of them can assume the module is already loaded. A failed import renders an in-page error (`renderLazyLoadError()` in `utils.js`) instead of crashing; `openReconcileModal` (reachable cold from the Ledger page's "Reconcile this account" button, not just the Reconcile nav page) shows `showAlertModal(...)` instead, since there's no Reconcile-page DOM to host an inline error in that case. **`reportsNetWorth.js`, `forecast.js`, and `spending.js` are deliberately kept static** — `reportsNetWorth.js`'s `renderNetWorthWidget()`/`captureNetWorthSnapshot()` are called from the Accounts page, `app.js`'s startup auto-snapshot logic, and `reconciliation.js`, not just the Reports page; `spending.js` is statically imported by `reports.js` (its `PINNED_COLORS` constant moved to `utils.js` in #329 to break a `spending.js → ledgerTransactions.js → recurring.js → spending.js` const-export import cycle — never import a `const` from `spending.js` into a module on that cycle). Do not add a new static import of any of the four lazy-module files from `app.js` or any always-loaded module (that would silently re-introduce the eager-load cost this issue removed) — route any new call site through the existing loader instead. See `docs/superpowers/specs/2026-10-25-dynamic-import-code-splitting-design.md`.

- **Migration safety guardrail:** All current `server/migrations/` `down()` functions are simple `DROP TABLE`/`DROP INDEX` (safe on brand-new empty tables/indexes). When the *first migration that alters a populated table* lands (e.g., adding a `NOT NULL` column to existing data), review whether its `down()` needs a safer rollback path — a blind `DROP` or destructive revert on real data is a different risk profile than the current CREATE-only migrations. Also: migration functions receive a `MigrationBuilder` (`pgm`) as their first argument — use `pgm.sql()` for raw SQL, not `db.query()` (which would throw `TypeError: db.query is not a function`).

- **Migration numbering is order-sensitive.** `server/src/index.js` runs `node-pg-migrate` on every startup. It refuses to run if an unapplied migration sorts before an applied one, which makes the server crash-loop and nginx return 502.
  - A new migration's number must be higher than the newest migration on `main` **at merge time**, not just when the branch was cut.
  - When parallel branches each add a migration, renumber whichever merges later above the one that merged first. Reserving numbers up front breaks if the merge order differs: 026 merged after 027 and took production down, which is why it is now `1755600000029`.
  - `server/scripts/check-migration-order.sh` (CI `test-server`, PRs only) enforces this against the base branch. Write new migrations idempotently (`IF NOT EXISTS` / `IF EXISTS`) so a renumber is always safe.

## Security constraints (enforced by tests in `tests/security/`)

- **Strict CSP** in `index.html`: `script-src 'self' https://cdn.jsdelivr.net`, `style-src 'self'` — no inline `<script>`, no inline `style="..."`, no `eval`/`Function()`. All dynamic styling must use CSS classes/variables (see `styles-csp-classes.css`) toggled via `classList`.
- **All user-supplied data rendered via `innerHTML` must go through `escapeHtml()`** (from `utils.js`). Prefer `textContent` where possible.
- **All persisted/imported fields must be sanitized** via the `sanitize*` functions in `sanitizers.js` / `utils.js` — never trust raw `localStorage` or imported JSON.
