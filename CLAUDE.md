# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

MyFinances is a privacy-first, self-hosted personal finance tracker (debt payoff planning, accounts, income, budgets, savings, net worth, cash flow forecasting). The frontend is **vanilla ES6+ JavaScript with no build step and no framework**; all calculations run in the browser. Since v7.0.0 the **self-hosted Node.js + PostgreSQL server (`server/`) is the only storage**: the app needs the Docker stack (nginx + server + Postgres) and keeps no financial data in browser storage. The only external frontend dependency is Chart.js, loaded via CDN.

## Commands

### Run the app locally
```bash
docker compose up -d                                                # http://localhost:32900
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d   # bind-mounts the frontend: edit, then refresh
```
A plain static file server no longer works: the app needs the API. The stack needs `secrets/postgres_password.txt` and `secrets/smtp_password.txt` (empty is fine); `setup.sh`/`setup.ps1` create them (see `DEPLOYMENT.md`). `docker-compose.dev.yml` mounts `index.html`, `guide.html`, `src/`, the stylesheets, `sw.js`, `manifest.json` and `icons/` read-only into nginx; it has only been checked with `docker compose config`, not run live.

### Tests
```bash
pip install playwright pytest pytest-asyncio
playwright install chromium

pytest tests/ -v                  # all tests
pytest tests/security/ -v         # XSS, CSP, input validation, static scan
pytest tests/features/ -v         # per-feature CRUD/business logic tests
```

`pytest.ini` sets `asyncio_mode = auto`. Custom markers (`security`, `feature`, `ui`, `integration`, `slow`) are registered in `tests/conftest.py`.

**Every Playwright test runs against a real stack** (`tests/conftest.py`). `app_page` wipes all server data per test, so **never point tests at a deployment holding real data**.
- **Env:** `TEST_BASE_URL` (default `http://localhost:32900/`), `TEST_EMAIL`, `TEST_PASSWORD`, falling back to `POSTGRES_TEST_EMAIL`/`POSTGRES_TEST_PASSWORD` (`tests/postgres/conftest.py` reads `POSTGRES_TEST_BASE_URL`).
- **Test user (create it once per fresh stack, or the run aborts):** `printf '%s\n%s\n' testuser@example.com 'ci-Test-Passphrase-2026!' | docker compose run --rm -T server node scripts/create-user.js` (stdin: email line, then password line; same as `.github/actions/start-stack`). These are the harness defaults; override with `TEST_EMAIL`/`TEST_PASSWORD`.
- **User:** `stack_user` registers only when `/auth/setup-status` reports `needsSetup` (which also needs `ALLOW_SETUP=true` on the server); otherwise it logs in, and fails loudly if that is rejected. The session cookies are cached in a temp file across pytest processes.
- **Fixtures/helpers:** `ensure_session(context)` installs the cookies (re-logging in on 401); `app_page` signs in, waits for readiness and calls `reset_server_state(page)` (`pgDeleteAll` + seeds `reconciliationAdjustsBalance` so the wizard stays away, then reloads); `seed_state(page, state)` replaces all server data with a JSON-export-shaped `state` through `replaceForPostgres` and reloads; `seed_state_from_app(page)` pushes in-memory `app.*` collections the same way; `wait_for_api(page, path, check, timeout)` polls a GET until the server holds a fire-and-forget mutation (use it before reloading to prove persistence). Async twins: `async_app_page`, `seed_state_async`, `reset_server_state_async`.
- **Never run two pytest processes against one stack**: they share one user and wipe each other's data.
- **Wait for async saves (issue #592).** `add*` functions push the record with a temporary `Date.now()` id and `await` the POST before swapping in the real id, re-rendering and resetting the form. Acting straight after Submit can pick that temporary id in a dropdown (the server 400s the linked record) or click `#debtFormToggle` while the form is still open, which closes it.
  - **Helpers** (`tests/conftest.py`): `submit_account_form(page)` / `submit_debt_form(page)` (and `_async` twins) click Submit and wait for the save to finish; `open_debt_form(page)` opens the Add Debt form only when it is closed.
  - **Guard:** `tests/features/test_async_submit_guard.py` (shard K) fails CI when an `#accountFormSubmit`/`#debtFormSubmit` click isn't followed by a wait. A click whose save is meant not to finish (validation rejection, a deliberately failed request) carries `# submit-no-wait: <reason>`.
  - **Other add forms** (income, recurring, savings) have the same timing; wait for their list entry before linking another record to them.
- **CI:** the `build-images` job builds both images once and uploads them as the `stack-images` artifact. Every Playwright job runs `.github/actions/start-stack`, which loads them, starts the stack, creates the test user with `server/scripts/create-user.js` (`ALLOW_SETUP` stays unset) and exports the `TEST_*`/`POSTGRES_TEST_*` env.
- **No element-missing skips (issue #544).** Never write `if not el: pytest.skip(...)`; assert instead, so a removed or renamed control fails. `tests/features/test_skip_guard.py` (shard K) scans for it; date- or environment-dependent skips are fine, and a genuine exception carries `# skip-ok: <reason>`.
- **Service worker vs. `page.route`:** the SW can serve JS modules past a `page.route` interception. Tests that stub module or API requests use `browser.new_context(service_workers='block')` (see `tests/features/test_code_splitting.py`).

Runs in CI as the `test-server` job against a `postgres:16-alpine` service container (issue #407 — before that, nothing ran this suite).

**App readiness in tests (issue #422):** `src/app.js` sets `<html data-app-ready="true">` once `new DebtTrackerApp()` and `init()` settle, even if startup fails, and also while boot waits at the unreachable gate, the login gate or a legacy-data prompt. The `app_page` fixture waits for that marker after `goto`, and wraps `page.reload()` so every reload waits too. **Lazy pages render asynchronously.** `switchPage('reconcile'|'reports')` returns before the lazy-loaded module renders. Reading the DOM straight away only used to pass because of the startup race. Seed inside `async () => { …; app.switchPage('reconcile'); await app.renderReconciliationPage(); }` (or `await app.renderReportsPage()`), or wait for a selector. `applyReconciliation` also awaits its module before showing `#alertModal`, so wait for `#alertModalOkBtn` to be visible first.

### Mutation testing
```bash
npm install
npm run test:unit       # Jest unit tests — tests/unit/*.test.js
npm run test:mutation    # Stryker — mutates the tested functions in src/debtCalculator.js, src/utils.js, src/sanitizers.js and re-runs the Jest suite per mutant
```
This is a separate, dev-only toolchain from the Python/Playwright suite above — Node/Jest/Stryker are never shipped to the browser (`index.html` is unaffected). Mutation is scoped to exactly the functions `tests/unit/*.test.js` imports (not whole files): the pure, DOM-free `calculatePaymentPlan`/`formatDate`/`calculateMonthsBetweenDates` in `debtCalculator.js`, `utils.js`'s tested formatting/sanitizing helpers, the record-shape sanitizers in `sanitizers.js`, the tested `retirementCalculator.js` functions, and all of `balanceHistoryCore.js`, `passwordPolicy.js` and `planSettingsPatch.js`. Feature modules taking `app`/DOM state are out of scope.

**Scope is by function name, not line number (issue #452).** `MUTATE_SCOPE` in `tools/strykerScope.mjs` lists names per file. `stryker.config.mjs` calls its `buildMutateGlobs()`, which parses each file with Babel at config-load time and emits exact `file:start-end` ranges. Hand-written ranges had drifted until most pointed at unrelated code. To change the scope, edit `MUTATE_SCOPE`, or add a function to `EXCLUDED` with a reason; never write line numbers. `tests/unit/strykerScope.test.js` (runs on PRs, unlike `mutation-testing`) fails when a name doesn't resolve to exactly one declaration, or when a unit test imports a function from a scoped file that is in neither list. `node tools/strykerScope.mjs` prints the resolved globs. See `docs/superpowers/specs/2026-08-02-stryker-js-mutation-testing-design.md`.

## Architecture

### No build step — two script-loading modes
`index.html` loads scripts in a specific order that matters:
```html
<script src="src/debtCalculator.js"></script>           <!-- classic script, global DebtCalculator -->
<script src="...chart.umd.min.js"></script>             <!-- Chart.js from CDN -->
<script type="module" src="src/app.js"></script>        <!-- ES module entry point -->
```
`debtCalculator.js` is the only non-module file (pure, side-effect-free calculation engine) and is exposed as a global. Everything else is an ES module imported from `src/app.js`.

### Central app object + feature-module delegation pattern
`src/app.js` defines `DebtTrackerApp`, instantiated once as `window.app` on `DOMContentLoaded`. It holds **all application state** (`this.debts`, `this.accounts`, `this.incomes`, `this.bills`, `this.expenses`, `this.recurringTemplates`, `this.emergencyFunds`, `this.sinkingFunds`, `this.monthlySnapshots`, `this.reconciliations`, `this.ledgerAmountOverrides`, etc.) plus UI state (`editingDebtId`, `liabilitiesSubTab`, `_reportMonthOffset`, `_forecastRangeMonths`, ...).

Every feature module (`debts.js`, `debtBreakEven.js`, `breakEven.js`, `accounts.js`, `income.js`, `bonusAdvisor.js`, `bills.js`, `recurring.js`, `recurringPaid.js`, `savings.js`, `reports.js`, `reportsNetWorth.js`, `reportsCalendar.js`, `reportsCashFlow.js`, `reportsMoneyFlowSankey.js`, `reportsVariance.js`, `reportsSummary.js`, `forecast.js`, `health.js`, `spending.js`, `ledger.js`, `ledgerTransactions.js`, `ledgerOverrides.js`, `ledgerCleared.js`, `passwordPolicy.js`, `passwordUi.js`, `securitySettings.js`, `reconciliation.js`, `strategy.js`, `strategyPlanCalculation.js`, `strategyCalendar.js`, `strategyComparison.js`, `strategySummaryTable.js`, `strategyScheduleTable.js`, `charts.js`, `ui.js`, `storage.js`, `sanitizers.js`, `dataExport.js`, `dataTransferModal.js`, `commandPalette.js`, `keyboardShortcuts.js`, `settings.js`, `setupWizard.js`, `loginGate.js`, `serverUnreachableGate.js`, `serviceWorker.js`, `i18n.js`, `utils.js`, `postgresSync.js`, `postgresImport.js`, `pgMigrationModal.js`, `guideNav.js`, `guideTheme.js`) exports plain functions that take the app instance as their **first argument** (e.g. `addDebt(app)`, `computeAccountBalance(app, accountId, year, month)`). `DebtTrackerApp` methods are thin wrappers that call these functions with `this`. When adding a feature, follow this same pattern — put logic in a module function `featureFn(app, ...)` and add a one-line delegating method on `DebtTrackerApp`.

### Module import constraints

`ui.js` and `postgresSync.js` participate in circular ES-module import cycles with domain feature modules (example: `postgresSync.js → ui.js → ledger.js → settings.js → postgresSync.js`). These cycles are safe **only** because every involved export is a hoisted `function` declaration — ESM resolves hoisted functions across cycles without a TDZ issue. **Never convert an export in `ui.js` or `postgresSync.js` from a `function` declaration to an arrow-function `const`** without first auditing all callers for cycle membership. An arrow-function `const` export that is read during module evaluation of a sibling in the cycle will throw a ReferenceError (TDZ crash) at startup.

`src/people.js` adds a new leg to this cycle: `ui.js → people.js → postgresSync.js → ui.js` (verified safe 2026-10-19). `people.js` imports `pgPost`, `pgPatch`, `pgDelete` from `postgresSync.js` and `showDeleteConfirmModal`, `showAlertModal`, `showPersonReplacementModal` from `ui.js`; `ui.js` imports `refreshPersonSelectors` from `people.js`. All eight `people.js` exports (`buildPersonOptionsHtml`, `refreshPersonSelectors`, `renderPeopleList`, `addPerson`, `deletePerson`, `startEditPerson`, `cancelEditPerson`, `saveEditPerson`) are hoisted `function` declarations — none are arrow-function `const` exports — so the cycle is safe.

### Page navigation
Top-level pages (`data-page` buttons in `index.html`): `health`, `accounts`, `income`, `liabilities` (Debts + Budget sub-tabs), `recurring`, `savings`, `strategy` (Plan), `reports`, `ledger`, `reconcile`. `switchPage(app, pageName)` in `src/ui.js` shows/hides page sections, records `app._currentPage`, and calls `renderPageData(app, pageName)` — the per-page `render*` dispatch — when adding a new page, register it there. `renderPageData` takes a `{ resetToDefaults }` option (default `true`) guarding view-state resets that should only happen when navigating into a page (Liabilities defaulting to its Debts subtab, Reports zeroing its month offset); `app.refreshCurrentPageData()` calls it with `resetToDefaults: false` to re-render the currently visible page in place after data changes underneath it (e.g. a JSON import) without disturbing the user's current view.

### Storage & data flow
- **The server is the only store (v7.0.0).** In-memory `app.*` state is loaded from Postgres at boot and every mutation is written back over the REST API. See `docs/superpowers/specs/2026-11-03-server-only-storage-design.md`.
- `storage.js` holds the boot probe, `loadFromPostgres`, `saveToStorage` and `clearAllData`. Sanitization lives in `sanitizers.js`; JSON export/import (current format version `"3.0"`) and CSV export live in `dataExport.js`.
- Every record type has a `sanitizeX()` function in `sanitizers.js` (e.g. `sanitizeAccount`, `sanitizeDebt`, `sanitizeIncome`, `sanitizeBill`, `sanitizeExpense`, `sanitizeLedgerOverrides`) that runs on import and on every server write, using the shared sanitizers from `utils.js` (`normalizeText`, `sanitizeFiniteNumber`, `sanitizeInteger`, `sanitizeDateISO`). **A new persisted field needs a sanitizer entry, a migration and a `columns` entry in its `server/src/routes/*.js` route**, or the server silently drops it. `server/test/fieldParity.test.js` fails when a key a frontend sanitizer emits has no column (exemptions go in its `NOT_PERSISTED`, with a reason).
- **Import warning collection (issue #291)** — `sanitizeParsedState(parsed, warnings)` takes an optional second `warnings` array; when passed, it's populated with one entry per coerced field (`{recordType, recordName, kind: 'coerced', field, from, to}`) and one per record/entry dropped entirely (`{recordType, recordName, kind: 'rejected', reason}`), across every importable collection including the `ledgerAmountOverrides`/`ledgerClearedTransactions` maps and the post-merge balance-history orphan filter. Omitting `warnings` (the legacy-data import in `pgMigrationModal.js`) costs nothing extra — only `dataExport.js`'s `importAllJSON` opts in. `dataTransferModal.js`'s `showImportResult(kind, message, warnings)` renders these as a collapsible `<details>` list (built with `createElement`/`textContent`, never `innerHTML` of the warning text) inside the Backup & Restore modal; a malformed-JSON hard failure stays in the same inline error banner (never a popup `alert()`-style modal, per the modal's established no-native-dialogs pattern — see `tests/ui/test_data_transfer_modal.py`) but now includes the native `JSON.parse` error message. When adding a new array collection to `sanitizeParsedState`, use the existing `_sanitizeRecordArray`/`_sanitizeValueArray` helpers rather than a bare `.map().filter()`, or it silently won't participate in warning collection.
- Import enforces a 2 MB max file size and supports legacy v1.0 (debts-only) files.
- `utils.js` also hosts shared formatting/date/number helpers (`formatShortDate`, `formatMonthYear`, `formatLongDate`, `formatPlanMonth`, `dateToISO`, `parseFiniteOrNull`, `getReportDate`, `countIncomePaydaysInMonth`, `dailyCompoundInterest`) — check there before adding a new local date/number formatter in a feature module.

### Storage (PostgreSQL)
- **Server.** `server/` is a Node.js + Express API over PostgreSQL. Tables mirror each `sanitizers.js` record shape; every write re-runs the matching frontend `sanitize*` function, imported by relative path from `server/src/sanitizers/index.js` (which is why the Docker build context is the repo root). Auth is argon2id + server-side sessions (opaque token hashed before storage, httpOnly/SameSite=Strict cookie, `Secure` from `req.secure` via `app.set('trust proxy', 1)`) with a CSRF double-submit token (`getCsrfCookie()` in `storage.js`) on every mutating request. The single user comes from `server/scripts/create-user.js` or the one-shot `POST /auth/register`, which 404s unless `ALLOW_SETUP=true`, is rate-limited and atomic (`INSERT ... WHERE NOT EXISTS`), and 409s once any user exists. See `server/README.md`.
- **Boot (`app.js` `init()`).**
  1. Removes the stale `debtTrackerStorageBackend` key.
  2. `probeServer()` (`storage.js`) does `GET /api/plan-settings` (200 = session, 401 = no session). Only without a session does it call `/auth/setup-status`, because that route allows 20 requests per 15 min; **never call setup-status on every load**. A 429 there counts as reachable (sign-in, not the unreachable gate). A network error, a timeout (`PROBE_TIMEOUT_MS`, 8 s), a non-JSON body or any other non-2xx means unreachable.
  3. Unreachable → `#serverUnreachableGate` (`src/serverUnreachableGate.js`, with a "Try again" button that re-probes). No session → `#loginGate` (`src/loginGate.js`, setup or sign-in mode).
  4. `loadFromPostgres(app)` fans out about 20 GETs under `LOAD_TIMEOUT_MS` (20 s). A 401 throws `SessionExpiredError` and boot re-probes (→ login gate); any other failure → unreachable gate.
  5. Legacy browser data, then first run (below), then the usual What's New/snapshot/render steps. Nothing renders from data while a gate is up, but `data-app-ready` is still set (`_markReadyBehindGate`), so tests can tell "stopped at a gate" from "hung".
- **First run** means the `reconciliationAdjustsBalance` setting is absent **and** the loaded dataset is empty (`_isFirstRun`). Only then does the setup wizard open, and not if a legacy prompt was shown.
- **Legacy browser data.** `app._handleLegacyBrowserData()` looks for a pre-7.0 `debtTrackerData` key. Empty server → import modal (`showPgMigrationModal`, `src/pgMigrationModal.js`); non-empty server → download-or-remove modal (`showLegacyDataCleanupModal`). Declining the import first downloads the raw JSON (`myfinances-browser-backup-YYYY-MM-DD.json`, same as the cleanup variant) and only then removes the key. The key is kept on Escape or a failed import, so the browser copy is never destroyed without a backup.
- **Writes.** Feature modules call `pgPost`/`pgPatch`/`pgDelete`/`pgPut` (`src/postgresSync.js`) right after their in-memory mutation, before `updateUI()`. `add*` functions are `async` because they await `pgPost` for the DB-assigned id. `saveToStorage(app, fields)` (name is historical) PATCHes only the named `/api/plan-settings` fields (issue #564), e.g. `app.saveToStorage(['budgetCategories'])`; the body is built by the pure `buildPlanSettingsPatch` in `src/planSettingsPatch.js`, whose `PLAN_SETTINGS_FIELDS` lists the names. **Record mutations never call it** (#521): they write their own record, and a whole-row save from a stale tab or device reverted settings changed elsewhere. With no known field it sends nothing and warns. Milestones are not a plan-settings field: awarding one POSTs `/api/plan-settings/milestones`. A 401 calls `requestLogin(app)` (the only way to open the gate; it shares one in-flight promise, so concurrent failures open one gate), then retries the write once with a fresh csrf cookie; a failed retry shows the banner. `init()` caps consecutive `SessionExpiredError` re-probes at 2 before showing the unreachable gate. A network error or other non-2xx shows the persistent `#syncErrorBanner` (`showSyncErrorBanner()` in `ui.js`). Updates are optimistic: there is no rollback.
- **Import** (`dataExport.js` → `src/postgresImport.js`). Every per-record fan-out (import, merge, both rollbacks, `pgDeleteAll`, `seedMissingBalanceHistory`) goes through `mapWithConcurrency(items, IMPORT_CONCURRENCY, fn)` from the pure `src/concurrency.js` (6 in flight, issue #519); never use a bare `Promise.all` over records, which made Chromium abort thousands of requests. Then: `replaceForPostgres` wipes the server, remaps FK ids, POSTs everything and restores the pre-import snapshot on failure; `mergeForPostgres` POSTs only name-unmatched records, PUTs keyed resources and rolls back only what it created. `clearAllData` calls `pgDeleteAll(app)` (every collection, plan-settings scalars and milestones).
- **Adding a CRUD resource** — follow `planHistory` (issue #162): table + migration, a route with its `columns` map, and an entry in `POSTGRES_RESOURCE_ENDPOINTS` (`storage.js`), `CRUD_RESOURCES` (`postgresImport.js`) and `ALL_RESOURCE_PATHS` (`postgresSync.js`); those loops are generic. A single object rides a `plan_settings` jsonb column instead (see Home purchase planning).
- **Browser storage allowlist** (spec §3): only device preferences (theme, locale, currency, last-seen version, Ledger filters and hidden columns), the `debtTrackerReconInProgress` draft, `getItem`/`removeItem` of legacy `debtTrackerData` (only in `app.js` and `pgMigrationModal.js`), and `removeItem` of `debtTrackerStorageBackend` (only in `app.js`). `tests/security/test_no_browser_financial_storage.py` enforces it statically over `src/**/*.js`, and `tests/features/test_server_only_storage.py::test_no_financial_keys_after_crud_pass` checks it at runtime. A new key must be added to the allowlist; financial data never goes in browser storage.
- **Service worker** precaches the shell (so the unreachable gate renders offline) and is network-only for `/api/`, `/auth/` and `/calendar.ics`.

### Versioning
`APP_VERSION` (`src/utils.js`) is a hand-maintained semver string shown in the app footer — there's no `package.json`/build step to derive it from, so it's the single source of truth for the running app's version. Every bump must land alongside a matching `## [x.y.z] — YYYY-MM-DD` entry at the top of `CHANGELOG.md`; `tests/features/test_versioning.py` enforces that the two stay in sync (and that changelog headings stay in descending order), since nothing else previously caught a version-only commit with no changelog entry (see #59). Every **minor** bump (`x.Y.0`) also needs a user-facing entry at the top of `WHATS_NEW_ENTRIES` in `src/ui.js` (the account menu's What's New modal; patch releases don't need one), and `sw.js`'s `CACHE_NAME` must match too (`tests/features/test_pwa.py`). `tests/features/test_whats_new.py` enforces What's New: newest entry's major.minor must equal `APP_VERSION`'s, and no CHANGELOG minor release may be missing — it drifted 6.41→6.48 unnoticed because that test file wasn't in any `ci.yml` shard. **Feature/UI CI shards list test files explicitly — a new `tests/features/`/`tests/ui/` file must be added to a shard in `.github/workflows/ci.yml` or it never runs in CI.** `tests/features/test_ci_shard_coverage.py` (issue #415, shard K) now fails CI when a file is missing from every shard, listed twice, or a shard references a deleted file — it was added after 16 files were found never to have run, 5 of them with rotted failures.

### Calculation engine
`src/debtCalculator.js` (`DebtCalculator`, global) is a pure, side-effect-free engine for payoff schedules — daily-compounding interest, four strategies (Avalanche, Snowball, Priority-Lowest, Priority-Highest), per-month stimulus, and a binary-search back-calculator for target payoff dates. Keep it free of DOM/state access; all rendering happens in `strategy.js`.

### Cross-cutting features
- **Bills** (`bills.js`) — the standalone Bills UI (`#billForm`/`#billList`) was intentionally removed 2026-05-29 in favor of Recurring Templates (`recurring.js`), and there is currently no reachable UI to add or edit a bill. `bills.js` still defines the full data model, sanitizer, and calculation logic, and `app.bills` remains a live data dependency read by `accounts.js`, `health.js`, `ledger.js`, and `strategy.js` — existing bills data (from an older export, or injected directly into app state) still round-trips through storage/import/export and flows through every calculation correctly. See `tests/features/test_bills.py`'s `test_no_reachable_bill_add_ui`, which documents this gap as intentional rather than a regression.
- **Accounts** (`accounts.js`) are the hub: income, debts, bills, expenses, bonuses, and recurring templates can all link to an `accountId`, and `computeAccountBalance()` projects an account's end-of-month balance from all linked items.
  - **Notes (#286).** Accounts carry an optional multi-line `notes` field, max 500 characters.
    - **Sanitizing.** `normalizeMultilineText()` in `utils.js` strips the same characters as `normalizeText`, but keeps `\n`.
    - **Card display.** Cards show the first line, cut at 80 characters. A longer or multi-line note gets a native `<details>` holding the full text.
    - **Postgres.** Stored in `accounts.notes`, added by migration `1755600000030`. The same migration added the previously missing `catch_up_eligible` and `hsa_coverage_type` columns (#451).
- **Ledger** (`ledger.js`) aggregates income, debts, bills, expenses, and recurring templates into a unified transaction list, with a modal-based amount-override system (`ledgerAmountOverrides`, keyed `type|id|accountId|date`) and a per-transaction Cleared checkbox (`ledgerCleared.js`, `app.ledgerClearedTransactions`, keyed the same way) that records whether/when a transaction actually posted — informational only, it does not affect running balances.
- **Reports/Forecast/Health** (`reports.js`, `forecast.js`, `health.js`) all derive from the same underlying account/income/debt/recurring data — when changing a data shape, check all three for consumers.
- **Net worth projection** (issue #335) — `computeNetWorthProjection(app, horizonMonths)` in `reportsNetWorth.js` grows assets by `monthlyIncome - nonDebtExpenses - cashPaidToDebtThisMonth` each month and sources liabilities from `app.lastPaymentPlan`'s real per-debt `balance`/`payment` schedule when one exists (debt principal is a dollar-for-dollar asset→liability transfer, not a net-worth change — only the cash actually paid and true expenses move it).   - **Recurring → Ledger:** the Mark-as-paid modal has one row per occurrence (row 0 keeps `#recurringActualAmountInput`). Entering the template amount removes the override. Unmark paid un-clears and removes overrides. $0 goes through `confirmZeroAmountAllowed`.
  - **Ledger → Recurring:** every Ledger Cleared toggle (row checkbox, bulk clear/unclear, "clear all") calls `app.syncRecurringPaidFromLedger(txIds)`. Any new code path that sets Cleared on a recurring row must call it too.
  - **`template.paidMonths` is a derived cache**, not state: a month is listed iff it has occurrences and all of them are fully cleared. It survives because `calendarFeed.js`, the server's `calendarGenerator.js` (reads `paid_months` from Postgres) and `isOverdue()` read it. A month with no occurrences right now (paused/skipped) is never re-derived, so pausing doesn't erase paid history.
  - **`template.paidAmounts` is legacy**; it was never persisted to Postgres. `reconcileRecurringPaidState(app)` runs after load and at the top of `renderRecurringPage`. It is idempotent and returns true when something changed (the caller saves). For each month in `paidMonths` it clears any uncleared legs, turning `paidAmounts[month]` into overrides. It then empties `paidAmounts` and re-derives `paidMonths` from every cleared recurring key.
  - **Known limit:** editing a template's day or account changes its occurrence keys, the same as every other Ledger override/cleared entry. The old-date cleared entries become orphans and the month drops out of `paidMonths` (the user re-marks it). Reconcile only auto-clears a `paidMonths` month when *no* `recurring|<id>|*|<that month>` key is cleared (true legacy data); it matches by template id and month, not by the current occurrence dates, so a date move can't make an owned month look legacy (fixed in 6.60.0 — before, the result depended on whether the old and new dates overlapped).

- **Migration safety guardrail:** Migrations now alter populated tables. `1755600000028`'s `down()` rewrites rows before restoring a check constraint, and `1755600000031` changed `debts.updated_at` from `timestamptz` to `date`; its `down()` drops the added columns but leaves that type alone, since the time of day is already gone. For any migration that touches existing data, write a `down()` that cannot fail on real rows, and add a `MIGRATION SAFETY NOTE` comment saying what a rollback discards. Also: migration functions receive a `MigrationBuilder` (`pgm`) as their first argument — use `pgm.sql()` for raw SQL, not `db.query()` (which would throw `TypeError: db.query is not a function`).

- **Migration numbering is order-sensitive.** `server/src/index.js` runs `node-pg-migrate` on every startup. It refuses to run if an unapplied migration sorts before an applied one, which makes the server crash-loop and nginx return 502.
  - A new migration's number must be higher than the newest migration on `main` **at merge time**, not just when the branch was cut.
  - When parallel branches each add a migration, renumber whichever merges later above the one that merged first. Reserving numbers up front breaks if the merge order differs: 026 merged after 027 and took production down, which is why it is now `1755600000029`.
  - `server/scripts/check-migration-order.sh` (CI `test-server`, PRs only) enforces this against the base branch. Write new migrations idempotently (`IF NOT EXISTS` / `IF EXISTS`) so a renumber is always safe.

## Security constraints (enforced by tests in `tests/security/`)

- **Strict CSP** in `index.html`: `script-src 'self' https://cdn.jsdelivr.net`, `style-src 'self'` — no inline `<script>`, no inline `style="..."`, no `eval`/`Function()`. All dynamic styling must use CSS classes/variables (see `styles-csp-classes.css`) toggled via `classList`.
- **All user-supplied data rendered via `innerHTML` must go through `escapeHtml()`** (from `utils.js`). Prefer `textContent` where possible.
- **All persisted/imported fields must be sanitized** via the `sanitize*` functions in `sanitizers.js` / `utils.js` — never trust imported JSON or legacy browser data.
- **Never interpolate raw DOM input text into `innerHTML`**, even from `<input type="date">`. Format the parsed value and `escapeHtml()` it. CodeQL `js/xss-through-dom` flags this; alert #172 was fixed in #380 with a guard in `tests/security/test_target_payoff_xss.py`.

## Branch protection and merging (issue #380)

- **Rulesets on `main`.** No force-push or deletion, for anyone. Every change goes through a PR; the admin bypass is **pull-request only**, so direct pushes are rejected. Required checks: `ci-complete`, `Analyze JavaScript`, `trivy`, `dependency-review`, plus the CodeQL/Trivy code-scanning gate (high or above). Approvals required: 0, since the owner is the sole maintainer and reviews each PR before merging. Details are in `SECURITY.md`.
- **Never use the override to merge a red PR, or one with a missing required check.** Fix it or leave it unmerged. Commits land under the owner's identity, so this binds every session.
- **`ci-complete` is the only required `ci.yml` check.** A new job must be added to its `needs:`, or `tests/features/test_ci_shard_coverage.py` fails. A job that can never run on a PR (only `mutation-testing` today) goes in that test's `NOT_GATING` set instead.
- **Don't merge PRs yourself**; open them and mark them ready once CI is green. The owner merges.
