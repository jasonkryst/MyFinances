# MyFinances i18n Audit — 2026-09-02

**Scope:** Verify translation coverage claims in `CLAUDE.md`, check locale
dictionary integrity, find hardcoded strings inside the claimed-translated
areas, check currency localization, note RTL readiness, confirm unit test
coverage, and propose a roadmap for extending i18n to the rest of the app.

**Method:** Static review of `src/i18n.js`, `src/locales/{en,es,pl}.js`,
`index.html`, `src/health.js`, `src/utils.js`; key-diff of the three locale
dictionaries; `npx jest tests/unit/i18n.test.js`; review of
`docs/superpowers/specs/2026-08-04-i18n-support-design.md` and
`tests/features/test_i18n.py` for documented intent and existing coverage.
No code was changed as part of this audit.

## Executive summary

The pilot-scope claim in `CLAUDE.md` ("only nav, toolbar, Settings modal, and
Health page are translated so far") is **accurate**. The `es`/`pl` dictionaries
are in perfect key-parity with `en` (111/111 keys each, no missing or extra
keys) — there is no case of a genuinely broken/silently-English string within
the pilot scope caused by a missing dictionary key.

Two real (if minor) gaps exist *inside* the claimed-translated areas: two
strings in the Settings modal (PostgreSQL storage option and note) and the
accessible chart-data-table content for both Health-page gauges are hardcoded
English, never routed through `t()`.

The most significant substantive finding is **not a bug**: `formatCurrency()`
hardcodes `currency: 'USD'` by deliberate, documented design
(`2026-08-04-i18n-support-design.md`: "Currency stays USD (no multi-currency
support); only formatting conventions change") and is explicitly asserted by
an existing test. A Polish-locale user still sees `$1 234,50` (US dollar
sign, Polish digit grouping) rather than PLN. This is flagged clearly per the
task brief, but it is a known, tested limitation, not an audit defect — true
multi-currency support (per-account currency, conversion, sanitizer changes)
is a materially larger feature than string translation.

Unit tests pass (6/6), and there is a substantial existing Playwright suite
(`tests/features/test_i18n.py`, 12 tests) covering live nav/Settings/Health
translation, persistence, and locale-aware currency/date formatting.

## Findings by severity

### High — none found
No crash, blank-render, or silently-broken-key issues in the pilot scope.

### Medium

**M1. Settings modal has two hardcoded English strings that bypass `t()`.**
`index.html`:
- Line 1155: `<option value="postgres">PostgreSQL (self-hosted server)</option>`
- Line 1158: `<p id="settingsStoragePostgresNote" class="modal-helper-text hidden">You are using PostgreSQL. Switching back to local or session storage is not supported.</p>`

Both live inside `#settingsModal`, which is otherwise fully covered by
`data-i18n`/`data-i18n-attr`. A Postgres-backend user on `es`/`pl` sees these
two strings in English regardless of locale. Fix is mechanical: add
`en`/`es`/`pl` keys (e.g. `settings.storagePostgres`,
`settings.storagePostgresNote`) and `data-i18n`/`data-i18n-attr` on the two
elements, same pattern as their siblings.

**M2. Health page's accessible chart-data-tables are entirely untranslated.**
`src/health.js` lines 351–368 — the two `renderChartDataTable()` calls that
back the DTI gauge and Savings gauge (the `.sr-only` `<table>` screen-reader
equivalent required by the project's own chart-accessibility convention) pass
fully hardcoded English:
```js
renderChartDataTable('healthDtiGauge', {
    caption: 'Debt-to-Income Ratio',
    columns: ['Metric', 'Value'],
    rows: [
        ['Debt-to-Income Ratio', `${dtiPct.toFixed(1)}%`],
        ['Monthly debt payments', formatCurrency(totalDebtMin)],
        ['Monthly income', formatCurrency(monthlyIncome)]
    ]
});
```
and similarly for `healthSavingsGauge` ('Savings Rate', 'Monthly amount
saved', 'Monthly income'). These are the *only* two `renderChartDataTable`
calls in `health.js`, and both are missed. Net effect: a screen-reader user
on a non-English locale gets a translated visible gauge label directly above
an English-only accessible table for the same data — an i18n gap that is
also an accessibility inconsistency worth prioritizing given the project's
explicit chart-a11y convention. Fix: route `caption`, `columns`, and row
labels through `t()` with new keys (e.g. `health.dtiTableCaption`,
`health.tableMetricCol`, `health.tableValueCol`, reuse existing
`health.perMonthDebt`/`health.perMonthIncome`/`health.perMonthSaved` phrasing
where sensible instead of new duplicate keys).

### Low / informational

**L1. Currency is not locale-aware (by design, tested, documented).**
`src/utils.js` `formatCurrency()`:
```js
export function formatCurrency(value) {
    return new Intl.NumberFormat(getIntlLocale(), {
        style: 'currency',
        currency: 'USD',
        minimumFractionDigits: 2,
        maximumFractionDigits: 2
    }).format(value);
}
```
`currency: 'USD'` is hardcoded; only `getIntlLocale()` (digit grouping,
decimal separator) varies. This is explicitly called out as an accepted
design decision in the original spec and is pinned by
`tests/features/test_i18n.py::test_format_currency_is_locale_aware`, which
asserts `formatCurrency(1234.5)` in `en` is `'$1,234.50'` and that switching
to `pl` only changes the digit-grouping character (comma appears) — it does
not assert or expect a currency-symbol/code change. Recommendation: keep as
documented behavior for now, but track it as a distinct, larger backlog item
("multi-currency support") separate from ordinary page-translation work,
since it's the one gap a non-English-speaking user is most likely to notice
immediately in a finance app (their currency literally never appears).

**L2. RTL readiness — not required yet, but CSS is not RTL-ready.**
`styles.css` uses ~69 physical-direction declarations (`margin-left`,
`margin-right`, `float: left/right`, `padding-left`, `padding-right`) and
zero logical-property equivalents (`margin-inline-*`, `padding-inline-*`,
`text-align: start/end`). `LOCALES` in `src/i18n.js` currently only contains
`en`/`es`/`pl`, all LTR, so this causes no active bug. Flagging only so a
future RTL locale (Arabic, Hebrew) is understood to require a CSS pass, not
just new dictionaries.

**L3. Minor scope inconsistency, not a bug.** The Ledger page's `<h2>📒
Ledger</h2>` title and print button (`index.html` lines 96–102) sit
structurally inside `<header>`, immediately after the fully-translated nav —
but the Ledger page itself is correctly out of pilot scope per `CLAUDE.md`,
so this is consistent with the documented boundary, just visually adjacent to
translated chrome. No action needed beyond folding it into the eventual
Ledger-page translation pass.

## Prioritized roadmap for remaining pages

Sizing below uses two proxies: static HTML line count in `index.html` (work
needed via `data-i18n` attributes) and rendering-module line count (work
needed via inline `t()` calls in template literals, `health.js`-style). Pages
whose HTML section is only a few lines are almost entirely JS-rendered and
will follow the Health-page pattern rather than the attribute pattern.

| Page | Static HTML (lines) | JS render module(s) (lines) | Rendering style |
|---|---|---|---|
| Accounts | 49 | `accounts.js` (261) | Mixed |
| Reconcile | 3 | `reconciliation.js` (334) | Almost fully JS-rendered |
| Income | 124 | `income.js` (440) | Mixed |
| Recurring | 93 | `recurring.js` (501) | Mixed |
| Savings | 3 | `savings.js` (676) | Almost fully JS-rendered |
| Strategy (Plan) | 177 | `strategy.js` + 4 sub-modules (801) | Mixed |
| Liabilities (Debts+Budget) | 218 (+3 budget shell) | `debts.js` + `bills.js` (1,135) | Mixed, two subtabs |
| Ledger | 7 (header only) | `ledger.js` + 3 sub-modules (1,028) | Almost fully JS-rendered |
| Reports | 84 | `reports.js` + 6 sub-modules (1,597) | Mixed, most complex |

**Recommended order:**

1. **Accounts** — smallest module (261 lines), it's the cross-cutting hub
   page (income/debts/bills/expenses all link here), high visibility, low
   effort. Good next pilot slice to validate the pattern scales beyond
   Health.
2. **Reconcile** — smallest JS module (334 lines), tiny static shell, single
   focused workflow (reconciliation modal + table).
3. **Income** — moderate size (440 lines / 124 HTML lines), single page, no
   subtabs.
4. **Recurring** — similar size to Income (501 / 93), template-driven CRUD
   list, should reuse whatever string patterns Income established.
5. **Savings** — larger (676 lines) but almost fully JS-rendered (emergency +
   sinking funds), no subtab complexity.
6. **Strategy (Plan)** — core feature users engage with heavily (801 lines
   across 5 modules + 177 static lines: summary table, schedule table,
   calendar, comparison view). Worth doing before Ledger/Reports given usage
   frequency, despite the higher line count.
7. **Liabilities (Debts + Budget)** — largest static shell (218 lines) and a
   sizable JS surface (1,135 lines) split across two subtabs; budget-specific
   strings should be separated from debt strings in the dictionary for
   clarity.
8. **Ledger** — 1,028 lines across 4 modules (transactions, overrides,
   cleared-tracking), almost entirely JS-rendered; do after Liabilities since
   ledger transaction descriptions are partly derived from debt/bill/income
   labels that should already have a translation pattern established by then.
9. **Reports** — largest and most complex (1,597 lines across 7 sub-modules:
   net worth, calendar, cash flow, money-flow Sankey, variance, summary).
   Recommend splitting into its own multi-phase follow-up (one sub-report per
   phase) rather than one large PR, given the module count and chart-heavy
   content (each chart also needs its `renderChartDataTable` call
   translated — see finding M2 for why that step is easy to miss).

Cross-cutting recommendation for every phase above: audit each page's
`renderChartDataTable()` calls at translation time, not after — M2 shows this
step is easy to skip even on a page (Health) that was otherwise fully
translated.
