## New findings

### Medium

**N1. People page nav button has no `data-i18n` attribute and no key in `en.js`.**

The People page was added in v6.10.0. Its nav button:

```html
<button class="page-button" data-page="people">People</button>
```

has no `data-i18n` attribute, and `nav.people` is not in `en.js`, `es.js`,
or `pl.js`. All other 13 nav buttons have `data-i18n="nav.*"` with
corresponding keys (including the newer `nav.retirement`). This is an
inconsistency: a user on `es`/`pl` sees their nav fully translated except the
"People" button. Fix: add `data-i18n="nav.people"` to the button and add
`'nav.people': 'People'` (en), `'nav.people': 'Personas'` (es), and
`'nav.people': 'Osoby'` (pl) — the same one-line pattern used for every other
nav entry.

### Low

**N2. Retirement page (v5.0.0) has no translation coverage.**

`src/retirement.js` is a fully JS-rendered module with no `t()` calls. The
Retirement page nav button does carry `data-i18n="nav.retirement"` (correctly
added when the nav key was created), and the Retirement section renders
correctly — but all page content (account cards, snapshot tables, projection
panel, chart titles, button labels) is hardcoded English.

**N3. Settings modal "Currency" label is hardcoded English.**

`index.html` line ~1185:

```html
<label for="settingCurrency">Currency</label>
```

No `data-i18n` attribute. The Currency section was added to the Settings modal
alongside the `getCurrencyCode()` feature, but the label was not wired into
the translation system. The adjacent "Language" label has `data-i18n="settings.language"`;
the Currency label should follow the same pattern. Suggest key `settings.currencyLabel`.

**N4. Three new Settings modal strings hardcoded English (no `data-i18n`).**

Three settings added since the September audit are untranslated:

- `<span>Show archived debts</span>` — new toggle in the Settings modal with
  no `data-i18n`.
- `<span>Show archived recurring templates</span>` — same gap.
- `<button>Send test email</button>` — the SMTP test button
  (`#settingsSendTestEmailBtn`) has no `data-i18n`.

These are structurally inside `#settingsModal`, which is otherwise fully
covered by `data-i18n`. Pattern is mechanical: add keys (e.g.
`settings.showArchivedDebts`, `settings.showArchivedRecurring`,
`settings.sendTestEmail`) to all three dictionaries and add `data-i18n` to
each element.

**N5. Surplus-analysis sparkline `renderChartDataTable()` call uses hardcoded English.**

`src/health.js` ~line 20192 (the new Surplus Analysis sparkline added in
v6.9.0) calls:

```js
renderChartDataTable('healthSurplusSparkline', {
    caption: `Projected balance over ${windowDays} days`,
    columns: ['Date', 'Balance'],
    rows: ...
});
```

Both the caption template and column headers are hardcoded English. The two
existing gauge SR-tables (finding M2 in the September audit) were fixed to use
`t()`, but this third table missed the same treatment. This is the same
audit-finding M2 pattern recurring for a new chart.

**N6. Currency selector options are not translatable.**

The `<select id="settingCurrency">` lists 20 currency options as static
`<option>` elements in `index.html` (e.g. `EUR — Euro`, `GBP — British Pound`).
These are not routed through `data-i18n` or `t()`. Unlike the other hardcoded
strings above, this one is low-priority: ISO currency names have widely
accepted translations but differ substantially by locale, and providing
accurate Spanish/Polish names for 20 currencies would be a larger localization
effort than a mechanical key addition. Flagged for awareness, not urgency.
