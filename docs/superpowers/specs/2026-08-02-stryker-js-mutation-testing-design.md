# Stryker.js mutation testing (Issue #52)

## Context

GitHub Issue #52 ("stryker.js") asks to "Implement stryker js testing." No further detail was given in the issue body or comments.

Stryker Mutator (`@stryker-mutator/core`) is a mutation-testing tool: it makes small deliberate edits ("mutants") to source code — flipping `<` to `<=`, `&&` to `||`, deleting a statement, etc. — then re-runs the test suite against each mutant. A mutant that still passes the suite ("survived") marks logic the tests don't actually verify. This checks test *quality*, not just line coverage.

MyFinances is a no-build-step vanilla-JS static app (per `CLAUDE.md`) with no `package.json`/npm and no JS test runner. Its entire test suite is Python/pytest + Playwright, driving a real browser end-to-end against `python -m http.server 5500` (`tests/{features,integration,ui,security,a11y}/`). Stryker needs a fast, in-process JS test runner (mutants are re-tested potentially hundreds of times) — a full Playwright browser cycle per mutant is impractically slow and Python-level assertions can't precisely target JS-internal logic. There is currently no JS unit test suite of any kind.

This spec adds a **dev-only** Node.js/Jest/Stryker toolchain, isolated from the shipped app. `index.html` and the browser runtime are unaffected — `debtCalculator.js`, `utils.js`, and `sanitizers.js` are loaded exactly as they are today; Node is only used to run tests and mutation analysis, never shipped.

Node.js (v26.5.1) and npm (11.17.0) were confirmed installed on the dev machine via nvm-for-windows during this session (`C:\nvm\v26.5.1\`), letting this be verified locally (real `npm install`, real `package-lock.json`, a real Jest run, and a real Stryker mutation score) before anything lands in CI.

## Goals

1. Add a `package.json` + `package-lock.json` at repo root with Jest, Stryker core, the Stryker Jest runner, and Babel (test-transform only) as devDependencies.
2. Write real Jest unit tests — both positive (happy-path) and negative (invalid input / edge case) — for the pure, DOM-free functions in `src/debtCalculator.js`, `src/utils.js`, and `src/sanitizers.js`, under a new `tests/unit/` directory.
3. Add Stryker config scoped to those three files, running against the new Jest suite.
4. Run Stryker locally to get a real mutation score, then set `thresholds.break` a few points below that real number (not a blind guess).
5. Add a new `mutation-testing` job to `.github/workflows/ci.yml` that installs Node, runs Jest, runs Stryker, uploads the HTML mutation report as a build artifact, and fails the build below the break threshold.
6. Update `CLAUDE.md`, `README.md`, `CHANGELOG.md` (+ matching `APP_VERSION` bump per `tests/features/test_versioning.py`), and `ROADMAP.md` if it references this work.

## Non-goals

- No mutation testing of DOM-coupled feature modules (`accounts.js`, `ledger.js`, `strategy.js`, etc.) — those take `app`/DOM state as input and would need a much heavier mocking layer. Out of scope for this first slice; the three chosen files are pure/side-effect-free and the highest-value, lowest-friction target (per `CLAUDE.md`'s existing note that `debtCalculator.js` is "free of DOM/state access").
- No migration of the existing Python/Playwright suite. It keeps testing the app end-to-end exactly as today; this is an additive, parallel toolchain.
- No bundler/build step for the shipped app — Node/npm/Jest/Stryker are dev-only tooling, not a runtime dependency. `index.html`'s script loading is untouched.
- No ESLint/Stylelint — out of scope, unrelated to this issue.
- No incremental Stryker mode (`--incremental`) — not needed at this scale; can be added later if mutation runs get slow.

## Components

### `package.json` (new, repo root)
- `devDependencies`: `jest`, `@stryker-mutator/core`, `@stryker-mutator/jest-runner`, `babel-jest`, `@babel/core`, `@babel/preset-env`.
- `scripts`: `test:unit` → `jest`, `test:mutation` → `stryker run`.
- `package-lock.json` generated by a real local `npm install` (not hand-written), so CI can use `npm ci` for reproducible installs.

### `babel.config.cjs` (new)
Test-tooling-only transform (`@babel/preset-env` targeting current Node) so Jest can load `utils.js`/`sanitizers.js`'s native `export function` syntax without requiring Jest's experimental native-ESM flags. Does not affect what ships to the browser.

### `jest.config.js` (new)
`testEnvironment: 'node'`, `testMatch: ['**/tests/unit/**/*.test.js']`.

### `stryker.config.mjs` (new)
```js
export default {
  packageManager: 'npm',
  testRunner: 'jest',
  reporters: ['html', 'clear-text', 'progress'],
  mutate: ['src/debtCalculator.js', 'src/utils.js', 'src/sanitizers.js'],
  jest: { configFile: 'jest.config.js' },
  thresholds: { high: <TBD from real run>, low: <TBD from real run>, break: <TBD from real run> },
};
```
Threshold numbers are placeholders here by design — filled in from the actual local mutation score obtained during implementation, not guessed.

### `tests/unit/` (new directory, new files)
- `debtCalculator.test.js` — targets `DebtCalculator.calculatePaymentPlan` (already has a CJS `module.exports` guard, so it's directly `require()`-able) and `calculateMonthsBetweenDates`/`formatDate`. Positive: standard avalanche/snowball/priority payoff runs produce expected payoff month and total interest. Negative: empty debts array throws, `monthlyPayment <= 0` throws, `monthlyPayment` below total minimums throws, a plan that would exceed 600 months throws.
- `utils.test.js` — targets `normalizeText`, `sanitizeFiniteNumber`, `sanitizeInteger`, `parseFiniteOrNull`, `sanitizeDateISO`, `dateToISO`, `formatShortDate`/`formatMonthYear`, `dailyCompoundInterest`, `formatCurrency`. Positive: valid inputs format/clamp/parse as expected. Negative: HTML-bearing/oversized text for `normalizeText`, `NaN`/`Infinity`/non-numeric strings for the numeric sanitizers, malformed date strings (`"not-a-date"`, `"2026-13-40"`) for `sanitizeDateISO`, out-of-range min/max clamping.
- `sanitizers.test.js` — targets `sanitizeAccount`, `sanitizeDebt`, `sanitizeIncome`, `sanitizeBill`, `sanitizeExpense`, `sanitizeRecurringTemplate` (the record-shape sanitizers not requiring app/DOM context). Positive: well-formed records round-trip with expected types/fields. Negative: missing required fields fall back to safe defaults, malicious strings (`<script>`, embedded quotes) get stripped per `normalizeText`, negative amounts/invalid enums get clamped or rejected per each sanitizer's own rules.

### `.github/workflows/ci.yml` (edit — new job)
New `mutation-testing` job: `actions/checkout@v4` → `actions/setup-node@v4` (Node major version matched to whatever generates the local `package-lock.json` during implementation — currently v26 via nvm — `cache: npm`) → `npm ci` → `npm run test:unit` → `npm run test:mutation` → upload `reports/mutation/html/` as a build artifact (`if: always()`, so the report is available even on failure). Fails the job (and thus the PR check) when the mutation score drops below `thresholds.break`.

### Documentation
- `CLAUDE.md`: new subsection (under Commands and/or Architecture) documenting the Jest+Stryker toolchain, its file scope, `npm run test:unit` / `npm run test:mutation`, and that it's dev-only tooling separate from the Python suite.
- `README.md`: setup instructions (Node version, `npm install`, how to run both commands) plus a CI badge for the new job, mirroring the existing CI/Docker badges.
- `CHANGELOG.md` + `src/utils.js` `APP_VERSION`: new entry + matching version bump (required together — enforced by `tests/features/test_versioning.py`).
- `ROADMAP.md`: update if it references JS testing/mutation testing/issue #52.

## Data flow

Local dev / CI: `npm ci` (or `npm install` for first-time local setup) → `npm run test:unit` (fast Jest feedback, no mutation) → `npm run test:mutation` (Stryker: runs Jest once as a baseline, generates mutants of the 3 in-scope files, re-runs Jest per mutant via the same `jest.config.js`, computes a mutation score, writes an HTML report to `reports/mutation/html/`).

## Error handling / edge cases

Covered by the "negative" test cases enumerated per file above — the point of this work is precisely to pin down behavior on invalid/boundary input (negative numbers, malformed dates, oversized/malicious strings, out-of-range values, empty collections) rather than assume it. Where a negative test reveals current behavior is *wrong* (not just untested), that's a separate bug to flag, not silently "fixed" as a side effect of this issue — this spec's job is testing infrastructure, not behavior changes to `debtCalculator.js`/`utils.js`/`sanitizers.js`.

## Testing

- `npm run test:unit` must pass before `npm run test:mutation` is meaningful.
- Real local Stryker run during implementation determines the actual mutation score and, from it, the `thresholds` values committed in `stryker.config.mjs`.
- Existing Python suite (`pytest tests/ -v`) is unaffected and re-run as a regression check that nothing in `src/` was changed by this work (it shouldn't be — this issue adds tests and tooling only, not behavior changes).
- The new CI `mutation-testing` job is the first real end-to-end verification of the CI wiring itself (local Node install is direct-path-only right now — `C:\nvm\v26.5.1\node.exe` — since PATH hasn't propagated to this shell session; CI uses a clean runner so isn't affected by that).
