## Storage & data flow
- **The server is the only store (v7.0.0).** In-memory `app.*` state is loaded from Postgres at boot and every mutation is written back over the REST API. See `docs/superpowers/specs/2026-11-03-server-only-storage-design.md`.
- `storage.js` holds the boot probe, `loadFromPostgres`, `saveToStorage` and `clearAllData`. Sanitization lives in `sanitizers.js`; JSON export/import and CSV export live in `dataExport.js`. An export stamps `version: APP_VERSION`; import does not read it (a legacy v1.0 file, a bare array of debts, is recognized by its shape).
- Every record type has a `sanitizeX()` function in `sanitizers.js` (e.g. `sanitizeAccount`, `sanitizeDebt`, `sanitizeIncome`, `sanitizeBill`, `sanitizeExpense`, `sanitizeLedgerOverrides`) that runs on import and on every server write, using the shared sanitizers from `utils.js` (`normalizeText`, `sanitizeFiniteNumber`, `sanitizeInteger`, `sanitizeDateISO`). **A new persisted field needs a sanitizer entry, a migration and a `columns` entry in its `server/src/routes/*.js` route**, or the server silently drops it. `server/test/fieldParity.test.js` fails when a key a frontend sanitizer emits has no column (exemptions go in its `NOT_PERSISTED`, with a reason). **A validity rule belongs in an exported `isValidX()` next to the sanitizer**, used by both `sanitizeParsedState` and the server route (`isValidManualTransaction`, `isValidTransfer`, `isValidReconciliation`, `isValidRecurringTemplate`; #568, #569): wrap the route's sanitize in `validatedSanitizer(sanitize, isValid, fields)` (`server/src/validity.js`), so a failed rule is a 400 on POST and on a PATCH that touches one of `fields` (an unrelated PATCH of a legacy invalid row still passes). Transfers are the exception: a DB CHECK backs the rule and re-checks the whole row on any UPDATE, so `routes/transfers.js` validates every PATCH. Never a rule that only the import path checks.
- **Import warning collection (issue #291)** — `sanitizeParsedState(parsed, warnings)` takes an optional second `warnings` array; when passed, it's populated with one entry per coerced field (`{recordType, recordName, kind: 'coerced', field, from, to}`) and one per record/entry dropped entirely (`{recordType, recordName, kind: 'rejected', reason}`), across every importable collection including the `ledgerAmountOverrides`/`ledgerClearedTransactions` maps and the post-merge balance-history orphan filter. Omitting `warnings` (the legacy-data import in `pgMigrationModal.js`) costs nothing extra — only `dataExport.js`'s `importAllJSON` opts in. `dataTransferModal.js`'s `showImportResult(kind, message, warnings)` renders these as a collapsible `<details>` list (built with `createElement`/`textContent`, never `innerHTML` of the warning text) inside the Settings → Backup & Restore page; a malformed-JSON hard failure stays in the same inline error banner (never a popup `alert()`-style modal, per the page's established no-native-dialogs pattern — see `tests/ui/test_data_transfer_modal.py`) but now includes the native `JSON.parse` error message. When adding a new array collection to `sanitizeParsedState`, use the existing `_sanitizeRecordArray`/`_sanitizeValueArray` helpers rather than a bare `.map().filter()`, or it silently won't participate in warning collection.
- Import enforces a 2 MB max file size and supports legacy v1.0 (debts-only) files.
- `utils.js` also hosts shared formatting/date/number helpers (`formatShortDate`, `formatMonthYear`, `formatLongDate`, `formatPlanMonth`, `dateToISO`, `parseFiniteOrNull`, `getReportDate`, `countIncomePaydaysInMonth`, `dailyCompoundInterest`) — check there before adding a new local date/number formatter in a feature module.

## Storage (PostgreSQL)
- **Server.** `server/` is a Node.js + Express API over PostgreSQL. Tables mirror each `sanitizers.js` record shape; every write re-runs the matching frontend `sanitize*` function, imported by relative path from `server/src/sanitizers/index.js` (which is why the Docker build context is the repo root). Auth is argon2id + server-side sessions (opaque token hashed before storage, httpOnly/SameSite=Strict cookie, `Secure` from `req.secure` via `app.set('trust proxy', 1)`) with a CSRF double-submit token (`getCsrfCookie()` in `storage.js`) on every mutating request. The single user comes from `server/scripts/create-user.js` or the one-shot `POST /auth/register`, which 404s unless `ALLOW_SETUP=true`, is rate-limited and atomic (`INSERT ... WHERE NOT EXISTS`), and 409s once any user exists. See `server/README.md`.
- **Boot (`app.js` `init()`).**
  1. Removes the stale `debtTrackerStorageBackend` key.
  2. `probeServer()` (`storage.js`) does `GET /api/plan-settings` (200 = session, 401 = no session). Only without a session does it call `/auth/setup-status`, because that route allows 20 requests per 15 min; **never call setup-status on every load**. A 429 there counts as reachable (sign-in, not the unreachable gate). A network error, a timeout (`PROBE_TIMEOUT_MS`, 8 s), a non-JSON body or any other non-2xx means unreachable. A signed-in probe returns the parsed body as `planSettings`, and `init()` passes it to `loadFromPostgres(app, { planSettings })` so a signed-in boot GETs `/api/plan-settings` once (#533); after the login gate, `refreshFromServer` or a re-probe it is fetched as usual.
  3. Unreachable → `#serverUnreachableGate` (`src/serverUnreachableGate.js`, with a "Try again" button that re-probes once and resolves with its probe result; `init()` reuses it as the next iteration's probe instead of probing again, #468). No session → `#loginGate` (`src/loginGate.js`, setup or sign-in mode).
  4. `loadFromPostgres(app)` fans out about 20 GETs under `LOAD_TIMEOUT_MS` (20 s). A 401 throws `SessionExpiredError` and boot re-probes (→ login gate); any other failure → unreachable gate.
  5. Legacy browser data, then first run (below), then the usual What's New/snapshot/render steps. Nothing renders from data while a gate is up, but `data-app-ready` is still set (`_markReadyBehindGate`), so tests can tell "stopped at a gate" from "hung".
- **Landing page only (#525).** After the data loads and the shared setup runs, `init()` yields a frame (`nextFrame()`, rAF with a 50 ms timer fallback), calls `updateUI({ deferHiddenPages: true })`, yields again, then `switchPage('health')`, so boot is several short tasks. `deferHiddenPages` still computes the saved plan (`restoreLastPlan({ display: false })`: Health and the debt cards read `lastSummary`) but skips `renderPlanHistory`, `renderDebtsList`, `renderNetWorthWidget` and the Plan results DOM; it sets `app._planDisplayPending`, which `renderPageData('strategy')` consumes on the first visit (`displayPaymentPlan` also clears it). Liabilities renders on first visit through `renderPageData` as always. Every other `updateUI()` call (mutations, refresh, import) is unchanged and renders everything. A test that reads hidden-page DOM after a reload must navigate to that page first; `tests/features/test_boot_landing_only.py` pins the behavior with DOM checks, not timings. Most of what remained was Health's surplus card formatting dates and amounts with a fresh `Intl` formatter per call; `utils.js` formatters are now cached per locale (`formatDateCached`), so **never call `toLocaleDateString`/`new Intl.*` per item in a render loop**; use or extend the cached helpers.
- **On-demand locales (#703).** The Lighthouse app LCP is gated by the bytes and number of module requests before the first Health paint (about 100 modules over HTTP/1.1's 6 connections on simulated slow 4G), not by the data fetch chain: starting the probe and data GETs early, dropping Chart.js and preloading every module were measured and gave nothing (preloading made it worse). Reducing the modules on the first-paint path is the remaining lever (#713).
  - **Only `en.js` is bundled.** `i18n.js` loads `es`/`pl` through `ensureLocaleLoaded(code)`; the `DOMContentLoaded` handler awaits it for the stored locale before `new DebtTrackerApp()`, and `preloadAllLocales()` runs on idle after boot. `setLocale` is always synchronous (the locale and Intl formatting switch at once); if the dictionary is missing, `t()` falls back to English until it loads, and then the static translations are re-applied and the page re-renders. Do not add `es.js`/`pl.js` back to the `modulepreload` hints. A 80-module `modulepreload` list was measured and made FCP/LCP worse, so the hints stay as they are.
- **First run** means the `reconciliationAdjustsBalance` setting is absent **and** the loaded dataset is empty (`_isFirstRun`). Only then does the setup wizard open. `init()` checks it after the legacy prompt has closed (#466), so a declined or dismissed import on an empty server opens the wizard in the same load (and the `autoNwSnapshot` default and the silent What's New mark apply the same way); an accepted import leaves data, so no wizard.
- **Legacy browser data.** `app._handleLegacyBrowserData()` looks for a pre-7.0 `debtTrackerData` key. Empty server → import modal (`showPgMigrationModal`, `src/pgMigrationModal.js`); non-empty server → download-or-remove modal (`showLegacyDataCleanupModal`). Declining the import first downloads the raw JSON (`myfinances-browser-backup-YYYY-MM-DD.json`, same as the cleanup variant) and only then removes the key. The key is kept on Escape or a failed import, so the browser copy is never destroyed without a backup. Boot awaits the modal for both variants.
- **Writes.** Feature modules call `pgPost`/`pgPatch`/`pgDelete`/`pgPut` (`src/postgresSync.js`) right after their in-memory mutation, before `updateUI()`. `add*` functions are `async` and create records with `pgCreate(app, collection, path, record)`, which POSTs first and pushes the record into `app[collection]` only with the server's id; on failure it returns `null`, the record is never added, and the caller returns before resetting its form (#460, #593). **Never push a new record into `app.*` before its POST succeeds**: a temporary id leaks into dropdowns and into later PATCHes. Add forms and modal confirm buttons are wrapped in `withBusy(root, fn)` (`utils.js`), which locks the controls while the save is pending and ignores a second submit (#459). `saveToStorage(app, fields)` (name is historical) PATCHes only the named `/api/plan-settings` fields (issue #564), e.g. `app.saveToStorage(['budgetCategories'])`; the body is built by the pure `buildPlanSettingsPatch` in `src/planSettingsPatch.js`, whose `PLAN_SETTINGS_FIELDS` lists the names. **Record mutations never call it** (#521): they write their own record, and a whole-row save from a stale tab or device reverted settings changed elsewhere. With no known field it sends nothing and warns. Milestones are not a plan-settings field: awarding one POSTs `/api/plan-settings/milestones`. A 401 calls `requestLogin(app)` (the only way to open the gate; it shares one in-flight promise, so concurrent failures open one gate), then retries the write once with a fresh csrf cookie; a failed retry shows the banner. `init()` caps consecutive `SessionExpiredError` re-probes at 2 before showing the unreachable gate; the count resets after a successful load and after a gate Retry (#462). A network error or other non-2xx shows the persistent `#syncErrorBanner` (`showSyncErrorBanner()` in `ui.js`). Edits and deletes are optimistic, with no rollback; creates are not (above).
  - **Row versions and diff-only PATCH (#578, #563).**
    - **Server.** Every `createCrudResource` table has `row_version` (migration `1755600000032`). `crudRouter` returns it as `rowVersion`, increments it on PATCH, and returns `409 CONFLICT` with `current` when a sent `rowVersion` is stale. An unversioned PATCH is accepted unchecked.
    - **Client.** `postgresSync.js` keeps a shadow (the last server-confirmed copy) per item path. It is seeded by `seedShadows(app)` at the end of `loadFromPostgres` and after every import or rollback, and updated by POST, PATCH and DELETE.
    - **`pgPatch`.** It diffs the body against the shadow (`diffFields` in the pure `src/recordVersions.js`), sends only the changed fields plus `rowVersion`, skips no-op saves, and queues PATCHes per record. It now returns a promise.
    - **On 409.** `classifyConflict` merges the other side's changes to untouched fields and resends. A same-field conflict opens `#syncConflictModal` (`showSyncConflictModal` in `ui.js`), where Escape means use the other version.
    - **Call sites** keep passing the whole record. **Any code that replaces a collection wholesale from server rows must call `seedShadows(app)`**, or the next edit goes out unversioned.
  - **Live refresh (#575, #565).** Every successful write fires `myfinances:data-written` (`DATA_WRITTEN_EVENT`). `src/liveRefresh.js` relays it on `BroadcastChannel('myfinances-sync')`, so other same-browser tabs refresh.
    - **Returning to a tab** triggers a refresh after `REFRESH_ON_FOCUS_SECONDS`: `window.__ENV__`, written by `docker-entrypoint.d/40-ga-env-config.sh`, default 60.
    - **`app.refreshFromServer()`** loads into a scratch object (`loadFromPostgres(obj, { seed: false })`) and applies it only if `currentWriteGeneration()` hasn't moved and `pendingWriteCount()` is 0. It keeps `VIEW_STATE_FIELDS`, then re-seeds shadows and re-renders.
    - **Deferral.** A refresh waits (`data-refresh-deferred` on `<html>`) while a write is pending, any `app.editing…Id` is set, a dialog is open, or a text field has focus; `data-last-refresh` records the outcome. A new `_ledger*`/`_forecast*` field set by `loadFromPostgres` must join `VIEW_STATE_FIELDS`, which a Jest guard enforces.
    - **Deleted elsewhere.** A record PATCH or DELETE that 404s calls `recordGone`, which shows `#recordGoneBanner` with Reload. It keeps the stale local copy until a refresh. Some tests inject in-memory-only records whose saves 404 and rely on that. A keyed DELETE 404 is silent.
- **Import** (`dataExport.js` → `src/postgresImport.js`). Every per-record fan-out (import, merge, both rollbacks, `pgDeleteAll`, `seedMissingBalanceHistory`) goes through `mapWithConcurrency(items, IMPORT_CONCURRENCY, fn)` from the pure `src/concurrency.js` (6 in flight, issue #519); never use a bare `Promise.all` over records, which made Chromium abort thousands of requests. Then: `replaceForPostgres` wipes the server, remaps FK ids, POSTs everything and restores the pre-import snapshot on failure; `mergeForPostgres` POSTs only name-unmatched records, PUTs keyed resources and rolls back only what it created. `clearAllData` calls `pgDeleteAll(app)` (every collection, plan-settings scalars and milestones). The settings that hold an account id (`surplusAccountId`, `notifyFilterAccount`) are remapped through the account id map before their PUTs; an unresolved one is dropped (a merge keeps the existing value, a replace falls back to the default), with a warning (pure `src/settingsRemap.js`, #651).
  - **Merge dedupes every collection by natural key (#567, #478).** The pure `src/mergeDedupe.js` (`mergeKeyFor`, `planMerge`) holds one key function per collection (names, or name+date, accountId, from+to+amount+date, ...). FK parts are compared after `remapFk`, and in-file repeats collapse to the first record (later ones resolve to its new id for Ledger key remapping). `mergeForPostgres` returns `{ skipped: { [field]: count } }` for the result message. **A new CRUD resource needs a `KEY_FNS` entry there**, or merge re-creates it on every re-import.
  - **Ledger keys are remapped too (#520).** Override and cleared keys embed ids (`type|sourceId|accountId|date`), so both modes rewrite them through the same id maps before the PUTs, using the pure `remapLedgerKey`/`remapLedgerEntries` in `src/ledgerKeyRemap.js`. Source ids map per type: `interest` uses the account map, and `savings` is resolved across emergency and sinking funds using the key's account segment. In merge mode, a name-matched record resolves to the existing record's id. Unresolvable keys are dropped, never stored, and `importAllJSON` gets one summary warning per map. **A new keyed transaction type needs an entry in `SOURCE_MAP_BY_TYPE`**, or its keys are dropped on every import.
- **Adding a CRUD resource** — follow `planHistory` (issue #162): table + migration (including `row_version integer NOT NULL DEFAULT 1`; `server/test/rowVersion.test.js` fails without it), a route with its `columns` map (plus `foreignKeys`, and `foreignKeyArrays` for id arrays such as `debts.personIds`, so a reference to another user's or a missing row is a 400; #557), and an entry in `POSTGRES_RESOURCE_ENDPOINTS` (`storage.js`), `USER_STATE_COLLECTIONS` (`server/src/jobs/loadUserState.js`; `server/test/jobs.test.js` keeps the two equal), `CRUD_RESOURCES` (`postgresImport.js`) and `RESOURCE_TABLES` (`src/resourceDeletion.js`); those loops are generic. Add a natural-key function to `KEY_FNS` in `src/mergeDedupe.js` too (merge-mode dedupe), and to the change log's table lists (see Change log). **If the new table has a foreign key to another app table, add it to `RESOURCE_PARENTS`** there. `pgDeleteAll` deletes in child-first layers derived from it (#608), because deleting a parent while its children are being deleted deadlocks in Postgres. `server/test/resourceDeletion.test.js` fails on an undeclared foreign key or an unlisted table-backed route. A single object rides a `plan_settings` jsonb column instead (see Home purchase planning).
- **Browser storage allowlist** (spec §3): only device preferences (theme, locale, currency, last-seen version and Ledger hidden columns), the `debtTrackerReconInProgress` draft, `getItem`/`removeItem` of legacy `debtTrackerData` (only in `app.js` and `pgMigrationModal.js`), `getItem`/`removeItem` of legacy `debtTrackerLedgerFilters` (only in `ledger.js`, #571; never written), and `removeItem` of `debtTrackerStorageBackend` (only in `app.js`). `tests/security/test_no_browser_financial_storage.py` enforces it statically over `src/**/*.js`, and `tests/features/test_server_only_storage.py::test_no_financial_keys_after_crud_pass` checks it at runtime. A new key must be added to the allowlist; financial data never goes in browser storage.
- **Read every response body (#461).** `/api` and `/auth` answer `no-store`, and an unread body keeps its connection pending (it once kept boot from reaching Playwright `networkidle`). Every `fetch` in `src/` reads its body or passes the response to `discardBody()` (`utils.js`, re-exported by `storage.js`), error branches included. `tests/features/test_response_bodies.py` tracks responses from boot through sign-out and sign-in.
- **Service worker** precaches the shell (so the unreachable gate renders offline) and is network-only for `/api/`, `/auth/` and `/calendar.ics`. Precached subresources (everything in `PRECACHE_URLS` except `/` and `/index.html`) are served cache-first from the versioned cache (#524; a miss falls back to network-first), while the document, every navigation and anything not precached stay network-first. The precache fetches with `cache: 'reload'`. The dev bind-mount override therefore needs a `CACHE_NAME` bump (or unregistering the worker) to show an edited asset. Chart.js's `<script>` is `defer` (#523), which still runs before the module `app.js`; `tests/features/test_perf_523_524_533.py` covers both.
