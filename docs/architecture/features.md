# Feature reference

<!-- Moved verbatim from CLAUDE.md for #539. CLAUDE.md keeps the rules in short form and points here; when a rule changes, update both. -->

One entry per feature, in the order CLAUDE.md used to list them. Search for the feature name or its issue number.

- **Bills** (`bills.js`) — the standalone Bills UI (`#billForm`/`#billList`) was intentionally removed 2026-05-29 in favor of Recurring Templates (`recurring.js`), and there is currently no reachable UI to add or edit a bill. `bills.js` still defines the full data model, sanitizer, and calculation logic, and `app.bills` remains a live data dependency read by `accounts.js`, `health.js`, `ledger.js`, and `strategy.js` — existing bills data (from an older export, or injected directly into app state) still round-trips through storage/import/export and flows through every calculation correctly. See `tests/features/test_bills.py`'s `test_no_reachable_bill_add_ui`, which documents this gap as intentional rather than a regression.
- **Accounts** (`accounts.js`) are the hub: income, debts, bills, expenses, bonuses, and recurring templates can all link to an `accountId`, and `computeAccountBalance()` projects an account's end-of-month balance from all linked items.
  - **Notes (#286).** Accounts carry an optional multi-line `notes` field, max 500 characters.
    - **Sanitizing.** `normalizeMultilineText()` in `utils.js` strips the same characters as `normalizeText`, but keeps `\n`.
    - **Card display.** Cards show the first line, cut at 80 characters. A longer or multi-line note gets a native `<details>` holding the full text.
    - **Postgres.** Stored in `accounts.notes`, added by migration `1755600000030`. The same migration added the previously missing `catch_up_eligible` and `hsa_coverage_type` columns (#451).
- **Ledger** (`ledger.js`) aggregates income, debts, bills, expenses, and recurring templates into a unified transaction list, with a modal-based amount-override system (`ledgerAmountOverrides`, keyed `type|id|accountId|date`) and a per-transaction Cleared checkbox (`ledgerCleared.js`, `app.ledgerClearedTransactions`, keyed the same way) that records whether/when a transaction actually posted — informational only, it does not affect running balances.
- **Projection cache (#518).** `buildProjectedAccountTransactions()` builds every account's projection at once, so a per-account loop over `computeAccountBalance()`/`getLedgerTransactionsForMonth()` used to rebuild it N times. `src/projectionCache.js` (a leaf module, no imports) memoizes it by window, only inside a synchronous `withProjectionCache(app, fn)` scope; `renderPageData`, `updateUI`, the Reports tab dispatcher and the Forecast/Accounts/Health/Net Worth renders open one, and the `pg*` write helpers invalidate it. **A new render that loops balances per account or per month should run inside a scope**, and must treat the returned map as read-only. Outside a scope nothing is cached. `getProjectionBuildCount()` (`projectionCore.js`, re-exported by `ledgerTransactions.js`) lets tests count real builds.
- **Shared pure projection core (#579).** The browser and the server run the same projection code. These modules are DOM-free and import-safe in Node (the server imports them by relative path):
  - `src/recurringOccurrences.js` holds `getRecurringOccurrencesInMonth` and `isEffectivelyPaused`.
  - `src/ledgerStateCore.js` holds the override and Cleared lookups (`getOverrideAmount`, `getEffectiveAmount`, `isCleared`, `getClearedAt`).
  - `src/projectionCore.js` holds `buildProjectedAccountTransactions`, `getLedgerTransactionsForMonth`, `computeAccountBalance` and `makeLedgerTransactionId`.
  - `src/netWorthCore.js` holds `computeSnapshotMetrics`, `buildNetWorthSnapshot` and `hasSnapshotInMonth`.
  - The old homes (`recurring.js`, `ledgerOverrides.js`, `ledgerCleared.js`, `ledgerTransactions.js`, `accounts.js`) re-export them, so existing imports keep working. **Never import `ui.js`, `postgresSync.js`, `settings.js`, `storage.js` or any other DOM/network module from these four**, or the server can't load them. A projection change made there reaches the server snapshot automatically.
- **Background jobs (#579, #536).** `server/src/jobs/` is an in-process scheduler, started only from `server/src/index.js` `main()` (never from `createApp()`, so server tests don't run jobs). It ticks 30 s after startup and then hourly. It is on by default; `JOBS_ENABLED=false` turns it off.
  - **Claiming.** A job is `{ name, periodKey(now), run({ now, log }) }`. `runJob` claims `(job_name, period_key)` in `job_runs` (migration `1755600000039`, not a user resource) with `INSERT ... ON CONFLICT`, so it runs once per period across restarts and processes. Period keys use the server's local time (`TZ`, UTC in Docker).
  - **Failures.** A failure is logged and recorded, never thrown, and retried on later ticks up to `MAX_ATTEMPTS` (5) per period. A run left `running` for over 60 minutes can be taken over. Jobs must be idempotent.
  - **Jobs.** `prune-sessions` (hourly: expired sessions, `job_runs` older than 90 days, and notifications older than 90 days except open balance alerts), `notifications` (hourly, #211, below) and `net-worth-snapshot` (monthly). The snapshot runs for every user (the `autoNwSnapshot` setting only governs the app's own capture on load), skips users with no accounts and no debts (a $0 row would hide the Net Worth live point for the month), skips a month that already has a snapshot, never overwrites a row and awards no milestones. It loads the user through `loadUserState` (each route's `crudConfig.listForUser`, the exact GET body), so its numbers equal the app's (`server/test/jobs.test.js` checks this).
  - **New jobs** go in the `JOBS` registry in `server/src/jobs/index.js`.
- **Notifications (#211).** Spec: `docs/superpowers/specs/2026-11-15-notifications-design.md`; server details in `server/README.md`.
  - **Rules.** The pure, Stryker-scoped `src/notificationsCore.js` (`computeNotificationEvents(app, now, prefs)`) returns `billDueSoon`/`billDueToday` (a debt, legacy bill or recurring outflow, not a transfer leg, not Cleared, due within `notifyDaysAhead` days), `lowBalance`, `zeroBalance` and `projectedLow` events. `zeroBalance` means overdrawn (below $0, never at exactly $0, since many accounts sit at $0), and `projectedLow` without a threshold also needs a projected balance below $0. "Balance today" is `startingBalance` plus this month's override-aware projected transactions dated today or earlier. Credit Card, Loan, Retirement, archived and muted (`muteBalanceAlerts`) accounts never raise balance alerts; a muted account's bill alerts still fire. It follows the shared-core import rules above.
  - **Server.** `server/src/jobs/notifications.js` (`checkNotificationsForUser`) stores events in `notifications` (unique `(user_id, dedupe_key)`), skips a balance event while its `episode_key` is open, resolves episodes no longer active, then emails `pending` rows per alert or as one digest (template `notificationEmail`, English). Routes are in `server/src/routes/notifications.js`; `POST /api/notifications/check` runs the check on demand (the Playwright tests use it, since CI stacks have jobs off).
  - **Settings.** `notifyBillDue`/`notifyLowBalance`/`notifyZeroBalance`/`notifyProjectedLow` (default on), `notifyDaysAhead` (0-30, default 3), `notifyChannel` (`both`/`email`/`inApp`) and `notifyDelivery` (`perEvent`/`digest`) are in `settingsSchema.js`; defaults are applied by `getNotificationPrefs`. Settings → Notifications (`src/notificationSettings.js`) writes only changed values on Done, and an invalid Days ahead keeps the modal open and saves nothing.
  - **Per account.** `accounts.lowBalanceThreshold` (`sanitizeLowBalanceThreshold`: a positive amount or null; migration `1755600000040`) and the "Don't notify" checkbox `accounts.muteBalanceAlerts` (only a real `true` mutes; migration `1755600000042`). Muting resolves the account's open balance alerts and cancels their pending emails on the next check, and the account editor runs that check on save.
  - **Sinking fund behind (#701).** Type `sinkingBehind` (setting `notifySinkingBehind`, default on; filter category `sinking`; view target Savings). The rule is the pure, Stryker-scoped `getSinkingAlertState(fund, todayISO)` in `src/sinkingFundSchedule.js`: a non-archived `target_date` fund alerts as `behind` when its live required monthly amount is at least `SINKING_BEHIND_ALERT_RATIO` (1.10, inclusive) times its stored planned `monthlyAllocation` (a planned 0 never alerts as behind), or as `pastDue` when its date has passed with money still to save; funded funds never alert. `computeNotificationEvents` emits one event per fund with episode key `sinkingBehind|<fundId>|<targetDate>|<kind>` (also in `activeEpisodes`), so behind turning past due is a new alert, repeats are suppressed, and the open alert resolves on catch-up, funding, a date change, archive or delete, or the setting going off. `params.kind` selects `notify.msg.sinkingBehind`/`sinkingPastDue` (and the English email lines).
  - **Client.** `src/notificationsCenter.js` (toolbar `#notificationsBtn`, `#notificationsPanel`) uses plain `fetch`, not `pgFetch`, so reading or marking alerts never touches the save chip or live refresh. The list loads after boot and after each live refresh. `pgDeleteAll` also sends `DELETE /api/notifications`. Alert text is built from stored params with `notify.msg.*` keys.
  - **Page (#643).** Spec: `docs/superpowers/specs/2026-11-17-notifications-page-design.md`. The bell's "View all" link and the command palette open the `notifications` page, rendered by lazy `src/notificationsPage.js` (via `lazyModules.js`) and registered in `renderPageData`.
    - **Filter.** The pure, Stryker-scoped `src/notificationsFilter.js` filters by Type (Bill due, Low balance, Overdrawn, Projected low) and Status (Unread default, Read, Active, Resolved, All) and groups by day. Also filters by Account and a From/To date range. The View → Ledger deep link reuses Ledger's `restoreSavedLedgerFiltersOnce(app)` (exported from `ledger.js`), then resets the account, category, date range and cleared filters. Accounts' and Spending's View in Ledger use it too with `{ skip: ['clearedFilter', 'pageSize'] }` (#645); a new saved Ledger filter goes in its one field table.
    - **Saved filters (#649).** Type, Status and Account persist as three per-user settings (`notifyFilterType`/`notifyFilterStatus`/`notifyFilterAccount`, in `settingsSchema.js`, not exported; written only when changed). **The bell and its badge follow them** (default Unread) and show a "Filtered: ..." line with Clear when non-default; From/To dates are page-only. `GET /api/notifications` and `POST /api/notifications/read-all` take optional `type`/`status`/`account` params (`typesForCategory`), so the count and Mark all read match. Live refresh refetches the bell. Empty text is `notify.emptyUnread`/`notify.emptyFiltered`. Import the `NOTIFY_FILTER_*` constants from `settingsSchema.js` (import-free), not `settings.js`, in modules near the import cycle.
    - **Shared state.** `notificationsCenter.js` exports `loadAllNotifications`, `markNotificationsRead`/`markNotificationsUnread` and `onNotificationsChange`, so the bell and the page stay in step. Bulk marks offer Undo through `offerUndo`.
    - **Routes.** `GET /api/notifications?limit` (1-500, default 50) returns `total`; `POST /api/notifications/read` and `/unread` take `{ ids }`.
    - **Keyboard.** j/k/x/e/Enter on the page, listed in `KEYBOARD_SHORTCUTS`.
- **Change log (#580).** `audit_log` (migration `1755600000043`) gets one row per create/update/delete through `crudRouter`/`keyedRouter` and the plan-settings PATCH, written by an `_audit` CTE in the same SQL statement (`server/src/audit.js`). No-op updates, rejected writes, FK cascades, jobs and Ledger/Forecast filter PATCHes are not logged. `GET`/`DELETE /api/audit-log` (`server/src/routes/auditLog.js`); `prune-sessions` drops rows older than 90 days. Settings → Change history (`history` page, lazy `src/changeHistory.js`, pure Stryker-scoped `src/changeHistoryCore.js`, plain `fetch` like the notifications bell) lists them; field names and values render in `<code translate="no">`, which the i18n render guard skips. Clear All Data calls `pgDeleteAuditLog` after `pgDeleteAll` (a replace import keeps the history), and `reset_server_state_http` empties it last. **A new CRUD table needs an `AUDITED_TABLES` entry, an `AUDIT_TABLE_ORDER` entry and a `history.table.<table>` key** (`server/test/auditLog.test.js` checks them against `RESOURCE_TABLES`). Details in `server/README.md`.
- **Reports/Forecast/Health** (`reports.js`, `forecast.js`, `health.js`) all derive from the same underlying account/income/debt/recurring data — when changing a data shape, check all three for consumers.
- **Net worth projection** (issue #335) — `computeNetWorthProjection(app, horizonMonths)` in `reportsNetWorth.js` grows assets by `monthlyIncome - nonDebtExpenses - cashPaidToDebtThisMonth` each month and sources liabilities from `app.lastPaymentPlan`'s real per-debt `balance`/`payment` schedule when one exists (debt principal is a dollar-for-dollar asset→liability transfer, not a net-worth change — only the cash actually paid and true expenses move it). Falls back to a flat `(income - expenses)` delta per month, no debt compounding, once a plan ends or none exists. The Net Worth report's trend chart renders this as a dashed continuation of the historical Net Worth line (two datasets sharing one label axis, the projected one null everywhere except the single point where it should visually connect) — selectable 1/3/5-year horizon (`app._netWorthProjectionYears`), independent of the existing 3/6/12-month history-range buttons (`app._netWorthRangeMonths`).
- **Net Worth trend without snapshots** (issues #574, #585) — `getNetWorthTrend(app, months)` (`reportsNetWorth.js`) feeds the Reports trend from the pure, Stryker-scoped `buildNetWorthTrend` in `src/netWorthEstimate.js`; each point has `kind: 'snapshot' | 'estimated' | 'live'`.
  - **Real wins.** A snapshot (including a server-written `source: 'auto'` one) always beats an estimate for its month. Estimates only fill gaps and the months before the first snapshot, never future months or months before the first usable history entry.
  - **Estimate math.** Balance history records debts and the history-tracked accounts (`HISTORY_TRACKED_ACCOUNT_TYPES` in `balanceHistoryCore.js`: Credit Card, Loan, Savings), so liabilities are each debt's last entry on or before the month (carried forward) and assets are today's balances of non-tracked accounts held flat plus tracked accounts' positive history balances (Credit Card/Loan entries are negative and add nothing; Savings is a positive asset, never a liability). A tracked account with no entry yet that early is held flat at its first entry's balance, so adopting tracking (seeded today) doesn't drop it from earlier estimates. Null-balance (fixed-amount) and malformed entries are ignored.
  - **Live point.** With no snapshot at all and any account or debt, the current month is `computeLiveNetWorth(app)` (the snapshot metrics, **never persisted by rendering**) and the projection starts from it; with no data the empty state stays.
  - **Rendering.** Estimates are a separate dashed dataset (`reports.nwEstimatedLabel`), tagged "estimated" in the history table and a Yes/No Estimated column in the `renderChartDataTable`.
  - **Auto snapshot default.** First run (`_isFirstRun`, no legacy prompt) stores `autoNwSnapshot` true if absent; existing users keep the default off. The startup auto-capture skips an empty dataset so a $0 snapshot can't hide the live point.
- **Spending year-over-year toggle** (issue #332) — `renderReportsSpending` (`spending.js`) supports a `app._spendingYoYMode` toggle swapping each category badge's baseline from the prior calendar month to the same month one year prior; `computeSpendingByCategory(app, year, month)` itself is unchanged (still always computes its own internal prior-month delta) — the YoY baseline is a separate `computeSpendingByCategory(app, year - 1, month)` call compared via a local `_totalsByCategory`/`_changeVsBaseline` helper pair, so a category with no prior-year data simply shows no badge instead of a misleading 0%.
- **Income Trend chart** (issue #262) — `renderIncomeTrendChart(app)` in `income.js` renders a trailing 12/24-month stacked bar (Regular Income vs. Bonuses, via `countIncomePaydaysInMonth`/`computeMonthlyBonusesForMonth`) with an optional dashed year-over-year overlay line; hidden via the `#incomeTrendCard` `hidden` class when there's no income or bonus data. Called from `renderIncomeList`/`renderBonusList` themselves (not a separate `renderPageData` dispatch entry) so it stays in sync with every add/edit/delete mutation on either list.
- **Income gross vs. net modeling** (issue #251) — income records gain an optional `withholdingPercent` field (0–99.9, default `0`, so an unset field is a no-op), sanitized in `sanitizeIncome()` and surviving export/import. `computeNetIncomeAmount(income)` (`src/utils.js`) derives take-home pay as `amount * (1 - withholdingPercent/100)`; `computeMonthlyIncomeForMonth()` now returns **net** (it's the single function every cash-flow call site — Health's DTI/savings/cash-flow card, Cash Flow summary, the Debt-to-Income chart, Home Purchase affordability, the Net Worth projection, Plan's suggested-payment/income widgets — already called, so withholding only needed to be applied once, there). `ledgerTransactions.js`'s generated income transactions also post the net amount, so everything downstream of the ledger stream (Account projections, Forecast, and the Cash Flow/Money Flow/Variance/Summary reports) inherits net automatically. The raw `amount` stays **gross** and is still what's edited in the Add/Edit Income forms and shown in the payoff/report calendars' per-event tooltips (which show every event type's raw entered amount, not just income's). Income cards show net as the primary amount with a gross tooltip/secondary line when withholding is set. Health's DTI card notes which basis (`health.dtiBasisNet`/`health.dtiBasisGross`) is active. Stored in Postgres via migration `1755600000022_add-withholding-percent-to-incomes.js` (`withholding_percent numeric NOT NULL DEFAULT 0`) and `/api/incomes`'s `columns` map — no sanitizer change needed server-side since `server/src/sanitizers/index.js` re-exports the frontend `sanitizeIncome()` by relative path.
- **Command palette** (`commandPalette.js`) — Ctrl/Cmd+K or the toolbar `#commandPaletteBtn` opens a searchable jump list across all pages plus common actions; initialized once from `ui.js`'s `initializeEventListeners()`. New pages should be added to its command list alongside `switchPage()`'s page-name mapping. Commands are rebuilt on every open with `t()`, so labels follow the locale.
  - **Record search (#686).** While typing, `filterPaletteItems` appends the records whose names match: `buildRecordEntries(app)` lists accounts, debts, incomes, recurring templates, emergency and sinking funds and people (archived records and ended incomes left out, each with the amount its card shows), and the pure, Stryker-scoped `matchRecords` (`src/paletteSearch.js`) folds case and accents, ranks name prefix, then word prefix, then substring, groups by `RECORD_TYPE_ORDER` and caps each type at `MAX_RECORDS_PER_TYPE`. Record options carry `data-record-type`; the group headings are `aria-hidden`, so the type is also in each option's hint.
  - **Jump.** `jumpToRecord(app, entry)` uses `RECORD_TARGETS` (page, savings sub-tab, the Edit button selector, the card class): it sets `app._revealDebtId`/`_revealRecurringId` so the paginated lists open the page holding the record (`pageContaining`), clears the Debt or Recurring filters when the card is still missing, scrolls, adds `.cmdpal-highlight` for `RECORD_HIGHLIGHT_MS` and focuses Edit (the palette does not restore focus for a record jump). **A new record type in the palette needs a `RECORD_TARGETS` entry, a `RECORD_TYPE_ORDER` slot and `palette.type.*`/`palette.group.*` keys.**
- **Keyboard shortcuts panel** (`keyboardShortcuts.js`) — `#keyboardShortcutsModal` is rendered entirely from the `KEYBOARD_SHORTCUTS` constant (opened via the command palette's "Keyboard shortcuts" command or the account menu's `#accountMenuShortcutsBtn`, delegating to `app.openKeyboardShortcuts()`). **When you wire a new `keydown` shortcut anywhere, add/update its entry in `KEYBOARD_SHORTCUTS`** — `tests/ui/test_keyboard_shortcuts.py` asserts the panel's rows match the constant 1:1.
- **Account menu keyboard model** (#494) — `initAccountMenu` (`ui.js`) follows the WAI-ARIA menu-button pattern: Enter, Space (a click with `detail === 0`) and ArrowDown on `#accountMenuBtn` open onto the first item, ArrowUp onto the last; inside the menu ArrowDown/ArrowUp move with wrap-around, Home/End jump, Escape closes and returns focus to the button, Tab/Shift+Tab close and let focus continue. The items carry `tabindex="-1"` (roving) and `aria-expanded` follows the state. This is menu-internal navigation, not a global shortcut, so it has no `KEYBOARD_SHORTCUTS` entry. Test: `tests/ui/test_account_menu_keyboard.py`.
- **Settings (7.20.0, replaces the #322 tabs)** — `#settingsModal` (markup in `index.html`, value loading and saving in `setupWizard.js`'s `initSettingsModal`, navigation in `src/settingsNav.js`) is a phone-style grouped list: `<nav id="settingsNav">` holds `button.settings-row[data-settings-page]` rows (Appearance, Language & Region, Notifications, Backup & Restore, Advanced, Change history, Security, About, plus the Danger zone row `#clearDataBtn`), and each page is a `section#settingsPage-<id>`.
  - **Layout.** At 768px and wider the list and the selected page sit side by side; below it the list shows first, a row drills in (`settings-shell--page`), and `#settingsBackBtn` or Escape (`handleSettingsEscape`) goes back. The last page is an in-memory variable (not persisted), and crossing the breakpoint keeps the current page. `openSettings(app, { page })` / `app.openSettings({ page })` opens a page directly; the account menu and the command palette use `{ page: 'backup' }`, and tests use `open_settings_page(page, name)`. Focus moves to the page heading on open (not into a control that may be hidden), Back returns it to the row, and Tab is trapped inside the modal (#495).
  - **Save on change, no Done button.** Each control writes through `setSetting`/`app.setLocale`/`setCurrencyCode` on its own `change`; `saveNotificationField(app, id)` (`notificationSettings.js`) does the same for the notification controls, and an invalid Days ahead shows its error and writes nothing. Closing or Escape never reverts. `pgPut` runs PUTs to one path in order, so two quick toggles end at the last value. A test that reloads after changing a setting must `wait_for_api` for it first.
  - **Backup & Restore is the `backup` page.** `dataTransferModal.js` (`initDataTransferModal`, `showImportResult`, `requestImportModeChoice`, `resetBackupPage`) binds to the controls on it; `resetBackupPage()` clears the previous import result on every open. The old Backup & Restore dialog and its tabs no longer exist. `tests/features/test_settings_redesign_guard.py` fails on a reference to the removed hooks and when a page lacks a `settings-<page>` `TRANSLATED_PAGES` entry. Switches are real checkboxes with `role="switch"`; row values and their accessible names come from `refreshSettingsRowValues()`.
  - **Adding a setting** means placing its control on the right page in `index.html` and a `change` handler in `initSettingsModal`; a new page needs an entry in `SETTINGS_PAGES`, a row, a section, locale keys and a `TRANSLATED_PAGES` entry. Spec: `docs/superpowers/specs/2026-11-20-settings-redesign-design.md`.
- **Health per-card credit utilization breakdown** (issue #281) — the Credit Utilization card's toggle (`renderCardUtilBreakdownHtml` in `health.js`) renders one row per `debtType: 'creditCard'` debt (not just ones with a limit set), including a `.health-card-util-name` span holding the debt's raw name. Health renders on every app load (it's the default landing page), and like every other page its markup stays in the DOM — just class-hidden — after navigating away, so an unscoped Playwright `text=<name>` locator elsewhere in the app can match this hidden span instead of the element a test actually means, and then time out waiting for it to become visible. Any test that creates a credit-card debt and later does `wait_for_selector('text=<that name>')` off the Health page must scope the locator to the page's own container (e.g. `#debtsList >> text=...` on Liabilities) — this bit `tests/postgres/test_postgres_mutations.py`'s `test_debt_delete_persists`/`test_debt_edit_form_renders` in CI.
- **Health credit factors explainer** (issue #337) — `renderCreditFactorsHtml()` in `health.js` appends a native `<details id="healthCreditFactors">` to the Credit Utilization card in both its data and empty states.
  - **Content:** the five standard factors, with a status line only where the app has data: aggregate utilization vs. 30%, the oldest valid `debtStartDate`, and the revolving (card with a limit) vs. installment count among non-archived, non-`fixedAmount` debts. It also links to AnnualCreditReport.com.
  - **Never a score:** no score, gauge, meter or point estimate, ever. `tests/features/test_health_credit_factors.py` asserts this.
  - **Strings:** all copy is `health.credit*` keys in en/es/pl.
  - **Card navigation:** the Health `[data-card-nav]` click handler skips targets inside `a, button, input, select, details`. Any new expandable inside a Health card should use `<details>`, or be added to that selector.
- **Ledger category filter + Spending cross-navigation** (issue #315) — `app._ledgerCategoryFilter` (default `'all'`) filters `getFilteredSortedLedgerTransactions` (`ledgerTransactions.js`) the same way the existing account/date/cleared filters do, stored with them on the server (`plan_settings.ledger_settings`, with `pageSize`; #571). The Spending report's category drill-down modal (`spending.js`'s `_openSpendingDrilldown`) has a "View in Ledger →" link that sets this filter plus `app._ledgerCrossNavLabel` (a breadcrumb string) and calls `switchPage(app, 'ledger')`; `switchPage()` (`ui.js`) clears `_ledgerCrossNavLabel` whenever navigating to any page other than `'ledger'`, so the breadcrumb only shows for the single visit it was set for.
- **Ledger filters live on the server (#571).** `plan_settings.ledger_settings` holds account, date range, sort, Status (`clearedFilter`), `categoryFilter` and `pageSize`. The one definition is `sanitizeLedgerSettings(record, dateRangeDefault)` (`sanitizers.js`, Stryker-scoped), used by import and by the route (whose default date range is `'all'`, the client's `'around7'`). `loadFromPostgres` sets `_ledgerCategoryFilter`/`_ledgerPageSize` (both in `VIEW_STATE_FIELDS`), and `buildPlanSettingsPatch` sends all six, storing the pre-cross-nav account, date range and category (`_ledgerPreCrossNav*`) while a Spending cross-nav shows. **The device copy `debtTrackerLedgerFilters` is migrated once:** the first `restoreSavedLedgerFiltersOnce(app)` applies its sanitized values (except `options.skip` keys, which keep the server value), PATCHes `ledgerSettings` and removes the key; nothing writes it again, so a second browser or device sees the same filters.
- **List pagination (#330).** Liabilities' debt list (`#debtsList`) and Recurring's template list (`#recurringList`) show 25 items per page.
  - **Helpers.** The pure, import-free, Stryker-scoped `src/pagination.js` (`paginateList(items, page, pageSize)` clamps the page into 1..totalPages) and `src/paginationUi.js` (`renderPagerHtml`, `pagerDirectionFromEvent`, `afterPagerRender`; reuses the Ledger's `.ledger-pagination` classes). The `<nav class="list-pager">` renders only when there is more than one page and holds Previous/Next (aria-labels name the list) plus a polite "Showing a-b of n" status. Clicks are delegated by each list's existing container `onclick`, and focus stays on the pressed button (or moves to the other one when it just disabled).
  - **Filter and sort first.** They run over the whole list; only the rendered slice changes. Debts paginate the **flat sorted+grouped order**: a group that spans a page boundary shows its heading on both pages, with the whole group's count and totals. Recurring has no grouping.
  - **Page state is session-only** (`app._debtListPage`, `app._recurringListPage`; not loaded from the server, so not in `VIEW_STATE_FIELDS`). A filter, sort or group change (and the Overdue toggle) sets it to 1, and `renderPageData` resets it when `resetToDefaults` is true (navigating in). - **App routing (path addresses) (#730).** Spec: `docs/superpowers/specs/2026-11-25-app-routing-design.md`. Every page has a path address, so Back, Forward, refresh and bookmarks work.
  - **Route table.** The pure `src/router.js` (no imports; statically imported by `ui.js`, so it is in `sw.js` `PRECACHE_URLS` and the first-paint budget) holds `ROUTE_PAGES`, `ROUTE_SUB_TABS`, `DEFAULT_SUB_TAB`, `buildPath` and `parseLocation`. Health is `/`, `strategy` is `/plan`, every other page is `/<page>`; Liabilities (`debts`, `expenses`), Savings (`emergency`, `sinking`, `home`) and Reports (the nine report tabs) add `/<page>/<sub-tab>`. **A new page or sub-tab joins this table** (and `ROUTE_PAGES` must equal the keys of `PAGE_SECTION_IDS` in `ui.js`).
  - **Record and apply.** A view changes only through `switchPage`, the sub-tab functions or Settings open/close, which call `recordView`/`recordSettings`/`leaveSettings` to write the address; `history.pushState`/`replaceState` are called only in `router.js` (except the login gate's `replaceState` that clears `?reset_token`). Back/Forward (`popstate`) and boot run `applyLocation`, which sets an `applying` flag so recording is suppressed: applying an address never pushes, so Forward keeps working. The router calls through `app.*` methods and imports nothing from `ui.js`, `postgresSync.js`, `settingsNav.js` or lazy modules. A signed-out deep link survives the sign-in gate (and a `?reset_token=` link still reaches the reset form); a deep link to a lazy page is not reset to defaults when `appFeatures.js` finishes loading.
  - **Push vs replace.** Clicking a page or sub-tab pushes, except when the address is already current (no entry, so Back never seems to do nothing). A non-canonical address (legacy `?page=`, unknown path, missing sub-tab, trailing slash) is rewritten with `replaceState`.
  - **Settings.** The address carries `?settings=<page>` (bare `?settings` is the narrow list) on the page path. Opening Settings pushes an entry marked `settings: true` in `history.state`; moving between Settings pages replaces (keeping the marker). Closing steps back with `history.back()` only when the entry on screen has the marker **and** the entry before it belongs to this page load (`currentIndex - 1 >= bootIndex`, `canStepBackOverSettings`); otherwise it replaces with the plain path. So a bookmarked address (no marker) and a refreshed one (the previous entry is from the discarded document, where `history.back()` would reload the whole app) close in place; after a refresh that leaves one duplicate history entry, by design. **Never `pushState` in the same task as a Settings close**: `leaveSettings()`'s `history.back()` is asynchronous and would undo it. Settings is lazy, so `applySettingsFromLocation` opens it from the address once its modal is initialised.
  - **Remembered sub-tabs.** Navigating to Liabilities resets to Debts; Savings and Reports remember the last sub-tab. `recordView` reads the sub-tab `switchPage` settled on, so the address matches what is shown. Back/Forward between sub-tabs of the page already showing calls `switchPage(page, { subTab, resetToDefaults: false })`, so it keeps the page's view state (Reports month and range, Liabilities expense month and debt list page) as a tab click does.
  - **Legacy links.** `/?page=<name>` still opens that page and is rewritten in place; the manifest shortcuts use path addresses (`/`, `/plan`, ...). The Ledger search term and filters never reach the URL.
  - **`<base href="/">` and anchors.** `index.html` has `<base href="/">` so relative asset paths resolve under `/liabilities/expenses`; that would make a bare `href="#id"` navigate to `/`, so a delegated handler in `ui.js` scrolls to the target and keeps the current path (bare `href="#"` links keep their own handlers). No nginx or CSP change: `nginx.conf` already falls back to `index.html`.
  - **Offline.** The service worker's fetch handler answers a failed `navigate` request that is not itself cached with the cached `/index.html` shell (`tests/unit/swNavigateFallback.test.js`), so a deep link opens offline.
  - **Back guard (#731, #734).** Back closes the innermost open overlay or inline edit before it navigates. Overlays add no history entries. **History index**: every entry the router writes carries `history.state = { mf: <index> }` (a push is the on-screen index + 1, a replace keeps it); `currentIndex`, `bootIndex` (the index at load, read back from `history.state` after a refresh) and `expected` (the index a `history.go` is heading to) track it. On `popstate` (unless it is the router's own step, tracked by `expected`) the router calls `closeInnermost(app)`; when something was open, Back or Forward over it is undone with ONE `history.go(currentIndex - newIndex)`: no `pushState`, so no entry is dropped or added, Forward keeps working and a multi-step Back (Android's long-press Back menu, `history.go(-2)`) returns to the starting entry in one step; the address is not applied. An entry without an index (written by other code, e.g. the login gate's `replaceState`) is unknown: the guard falls back to restoring `lastPath` with `pushState`. `topOverlay()` finds the overlay (`[role="dialog"]`, `[role="alertdialog"]`, `.modal`, `[data-overlay]` that is shown; not a gate, not `#settingsModal`), preferring the one holding focus, and Back sends it an Escape keydown, so **a new overlay must close on Escape** and must not push history. The notifications panel and the account menu (popovers, registered with `notePopoverOpened`) count as overlays but rank below any dialog; both close on Escape (claimed in the capture phase through `claimEscape(e, el)`, so only the top overlay reacts) and return focus to their trigger. The More sheet leaves Escape to a dialog appended above it, so one Escape closes the dialog and the next closes the sheet. Gates (`GATE_IDS`: `#loginGate`, `#serverUnreachableGate`) are never closed; with one up Back applies the address as usual. Settings closes through its address (below), so a dialog over Settings closes alone (one Back), then the next Back closes Settings. Inline edits are cancelled as their Cancel button does, only while their edit UI is shown (`EDIT_INPUT_PREFIX` names each name input; `switchPage` leaves `editing*Id` set, and a hidden edit must not swallow Back): `EDIT_CANCELLERS` maps `editingAccountId` to `cancelEditAccount`, `editingBonusId` to `cancelEditBonus`, `editingExpenseId` to `cancelEditExpense`, `editingIncomeId` to `cancelEditIncome`, `editingPersonId` to `cancelEditPerson`, `editingRecurringId` to `cancelEditRecurring`; `editingDebtId` is handled apart (`cancelInlineEdit`); `editingBillId` never counts (no edit UI). **Recording**: `switchPage` records the view in a `finally`, so a render that throws still updates the address. **Settings marker and close**: Settings' opening push is written with `state.settings = true`; closing steps back (`history.back()`) only when the entry on screen has that marker AND the previous entry belongs to this document (`index - 1 >= bootIndex`, so a refresh or a bookmarked `?settings=` never steps back across a document and reloads the app); otherwise it replaces with the plain path in place. A command-palette choice of the page already under Settings steps back too: the palette closes Settings first (`isSettingsOpen` decides that), and `recordView` then applies the same marker and `bootIndex` rule through `canStepBackOverSettings`. **Apply-time Settings page**: `applySettingsFromLocation` records the page it actually shows after the address is applied, so a bare or unknown `?settings` on a wide screen and narrow-to-wide resizes rewrite the address to the page shown. `tests/ui/test_back_overlays.py` audits that every dialog closes on Escape. **Known limitations**: after a refresh, closing Settings replaces in place and leaves one duplicate history entry (a cross-document `history.back()` would reload the app); a Settings entry reached by Forward after a refresh can still pass the `bootIndex` check and cost one reload; the More sheet still takes Escape when focus stays inside it as a dialog is appended above it (real dialogs move focus into themselves); with both popovers open the second Back or Escape closes the account menu and leaves focus on the bell; and an Escape handler that navigates (none today) would invalidate the undo's `history.go` target.
