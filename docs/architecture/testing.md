## Playwright suite
```bash
pip install playwright pytest pytest-asyncio
playwright install chromium

pytest tests/ -v                  # all tests
pytest tests/security/ -v         # XSS, CSP, input validation, static scan
pytest tests/features/ -v         # per-feature CRUD/business logic tests
pytest tests/ui/ -v                # mobile, modals, dark mode, accessibility
pytest tests/integration/ -v       # end-to-end workflows / smoke tests
pytest -m "not slow" -v             # skip slow tests

# Single file / single test
pytest tests/features/test_debts.py -v
pytest tests/features/test_debts.py::test_add_debt -v
```
`pytest.ini` sets `asyncio_mode = auto`. `tests/requirements.txt` pins exact versions (#559; Dependabot bumps them, and the Playwright browser cache key hashes the file). Custom markers (`security`, `feature`, `ui`, `integration`, `slow`) are registered in `tests/conftest.py`.

**Every Playwright test runs against a real stack** (`tests/conftest.py`). `app_page` wipes all server data per test, so **never point tests at a deployment holding real data**.
- **Env:** `TEST_BASE_URL` (default `http://localhost:32900/`), `TEST_EMAIL`, `TEST_PASSWORD`, falling back to `POSTGRES_TEST_EMAIL`/`POSTGRES_TEST_PASSWORD` (`tests/postgres/conftest.py` reads `POSTGRES_TEST_BASE_URL`).
- **Test user (create it once per fresh stack, or the run aborts):** `printf '%s\n%s\n' testuser@example.com 'ci-Test-Passphrase-2026!' | docker compose run --rm -T server node scripts/create-user.js` (stdin: email line, then password line; same as `.github/actions/start-stack`). These are the harness defaults; override with `TEST_EMAIL`/`TEST_PASSWORD`.
- **User:** `stack_user` logs in, and fails loudly if that is rejected. It registers only with the opt-in `TEST_ALLOW_REGISTER=1`, when `/auth/setup-status` reports `needsSetup` (which also needs `ALLOW_SETUP=true` on the server); without it a fresh stack aborts with instructions to run `create-user.js` (#558). The session cookies are cached across pytest processes in a temp file (atomic write, 0600; a 401 re-login skips the cache, #475).
- **Fixtures/helpers:** `ensure_session(context)` installs the cookies (re-logging in on 401); `app_page` signs in, wipes the server over HTTP with `reset_server_state_http()` (the same layers and calls as `pgDeleteAll`, plus `reconciliationAdjustsBalance` so the wizard stays away), then loads the app once and waits for readiness (#550; `tests/features/test_harness_reset.py` keeps the HTTP wipe equal to `pgDeleteAll`, so a new call there must be added to `_RESET_EXTRA_CALLS`); `reset_server_state(page)` still wipes through the app and reloads, for mid-test resets; `browser` is session-scoped (one Chromium per pytest process) and `page` gets a fresh context, so a test that takes `browser` must create and close its own context and never close the browser; `seed_state(page, state)` replaces all server data with a JSON-export-shaped `state` through `replaceForPostgres` and reloads; `seed_state_from_app(page)` pushes in-memory `app.*` collections the same way; `wait_for_api(page, path, check, timeout)` polls a GET until the server holds a fire-and-forget mutation (use it before reloading to prove persistence). Async twins: `async_app_page`, `seed_state_async`, `reset_server_state_async`.
- **Never run two pytest processes against one stack**: they share one user and wipe each other's data. Enforced (#558): the first test that needs the stack's session takes an exclusive file lock (`tests/harness_support.py`, keyed on the API root, in the temp dir) and a second process exits at once naming the lock file; `TEST_SKIP_STACK_LOCK=1` bypasses it. Pure tests never lock.
- **Fail-fast CI (#551, #527, #469).**
  - **Timeouts.** `pytest.ini` sets `timeout = 120` (pytest-timeout, in `tests/requirements.txt`), so a hung test or fixture, including a hung boot, fails with a traceback. A test that really needs longer gets `@pytest.mark.timeout(n)`; none does (the slowest is about 17 s).
  - **CI.** Every pytest job passes `--maxfail=15` and has `timeout-minutes: 15`. `tests/features/test_ci_fail_fast.py` (shard K) enforces both, the ini setting, the requirement and the start-stack diagnostics.
  - **Shard budget.** Keep each Playwright shard under about 360 s of pytest (about 7.5 min job, since setup adds about 70 s). Balance by measured seconds per file, not test count. **Setup is fixed per job (#528)**, so don't add a shard with under ~150 s of pytest: put the files in an existing one. `test-integration` also runs `tests/a11y` and `tests/security`, and no job tears the stack down (the runner is discarded); `test_ci_shard_coverage.py` checks every whole-directory suite still runs. `test-features-l`/`-m` are the i18n render guard (seeded/empty state) and grow with `TRANSLATED_PAGES`; split by page name next when either nears the budget.
  - **start-stack** (`.github/actions/start-stack`). It first reserves port 32900 from the kernel's ephemeral range (`ip_local_reserved_ports`; an outgoing connection's TIME_WAIT on that port made Docker's bind fail), then waits up to 90 s until no socket of any state uses it (`ss -tan`, not just listeners), then waits up to 120 s for the frontend and 120 s for a healthy server. On failure it prints `docker compose ps -a` plus the last 200 log lines of every service, runs `down -v` and retries once. The create-user step prints the server logs on failure. It starts the stack with `JOBS_ENABLED=false` (#579), so no background job writes data mid-test; server tests call the jobs directly. The policy is written in the action's `description`.
- **Wait for async saves (issue #592).** `add*` functions `await` the POST and only then add the record to `app.*` (with its server id), re-render and reset the form (#460, #593). Until then the record is in no list or dropdown, and the form is locked (`aria-busy`, Submit disabled, text fields read-only; #459). Playwright's `fill`/`click` wait for an editable or enabled control, so they wait out the lock, but reading the list straight after Submit does not. Clicking `#debtFormToggle` while the form is still open closes it.
  - **Helpers** (`tests/conftest.py`): `submit_account_form(page)` / `submit_debt_form(page)` (and `_async` twins) click Submit and wait for the save to finish; `open_debt_form(page)` opens the Add Debt form only when it is closed.
  - **Guard:** `tests/features/test_async_submit_guard.py` (shard K) fails CI when an `#accountFormSubmit`/`#debtFormSubmit` click isn't followed by a wait. A click whose save is meant not to finish (validation rejection, a deliberately failed request) carries `# submit-no-wait: <reason>`.
  - **Other add forms** (income, recurring, savings) have the same timing; wait for their list entry before linking another record to them.
- **CI:** the `build-images` job builds both images once and uploads them as the `stack-images` artifact. Every Playwright job installs the browser with `.github/actions/install-playwright`, never `playwright install --with-deps`. The action runs `playwright install chromium`, checks that Chromium actually launches, and only then falls back to `playwright install-deps` through apt, with a timeout and one retry. GitHub's Ubuntu image already has Chrome's libraries, so an Ubuntu mirror outage no longer fails every job before a test runs; it did on 2026-11-11. `test_ci_shard_coverage.py` enforces this. The job then runs `.github/actions/start-stack`, which loads them, starts the stack, creates the test user with `server/scripts/create-user.js` (`ALLOW_SETUP` stays unset) and exports the `TEST_*`/`POSTGRES_TEST_*` env.
- **No element-missing skips (issue #544).** Never write `if not el: pytest.skip(...)`; assert instead, so a removed or renamed control fails. `tests/features/test_skip_guard.py` (shard K) scans for it; date- or environment-dependent skips are fine, and a genuine exception carries `# skip-ok: <reason>`.
- **Lighthouse is signed in (#470).** The `lighthouse` job runs `tools/lighthouseAuth.mjs setup` after `start-stack`: it logs in with the test user over HTTP, stores `reconciliationAdjustsBalance` (no setup wizard over Health) and writes the git-ignored `lighthouserc.auth.json`, a copy of `lighthouserc.json` whose `extraHeaders` carry the `session`/`csrf` cookies. LHCI runs with `--config=lighthouserc.auth.json`, then `lighthouseAuth.mjs verify` fails unless every non-guide run saw 200 on `/api/accounts` and `/api/debts` and no `/auth/setup-status` call (the login gate's probe), so a regression to auditing the sign-in screen fails CI.
- **Service worker vs. `page.route`:** the SW can serve JS modules past a `page.route` interception. Tests that stub module or API requests use `browser.new_context(service_workers='block')` (see `tests/features/test_code_splitting.py`).

## Server tests
```bash
cd server
docker compose -f docker-compose.test.yml up -d   # Postgres on :5433
export DATABASE_URL="postgres://myfinances_test:myfinances_test@localhost:5433/myfinances_test"
npm run migrate up && npm test                   # node:test, server/test/*.test.js
```
Runs in CI as the `test-server` job against a `postgres:16-alpine` service container (issue #407 — before that, nothing ran this suite).

**App readiness in tests (issue #422):** `src/app.js` sets `<html data-app-ready="true">` once `new DebtTrackerApp()` and `init()` settle, even if startup fails, and also while boot waits at the unreachable gate, the login gate or a legacy-data prompt. The `app_page` fixture waits for that marker after `goto`, and wraps `page.reload()` so every reload waits too. For a raw `page` fixture, or for a `goto`, call `tests.conftest.wait_for_app_ready(page)`.

**Lazy pages render asynchronously.** `switchPage('reconcile'|'reports')` returns before the lazy-loaded module renders. Reading the DOM straight away only used to pass because of the startup race. Seed inside `async () => { …; app.switchPage('reconcile'); await app.renderReconciliationPage(); }` (or `await app.renderReportsPage()`), or wait for a selector. `applyReconciliation` also awaits its module before showing `#alertModal`, so wait for `#alertModalOkBtn` to be visible first.

## Mutation testing
```bash
npm install
npm run test:unit       # Jest unit tests — tests/unit/*.test.js
npm run test:mutation    # Stryker — mutates the tested functions in src/debtCalculator.js, src/utils.js, src/sanitizers.js and re-runs the Jest suite per mutant
```
This is a separate, dev-only toolchain from the Python/Playwright suite above — Node/Jest/Stryker are never shipped to the browser (`index.html` is unaffected). `package.json`'s `overrides` pins `minimatch` to `^11.0.8` (GHSA-g3hv-75wg-m249; `test-exclude@7` still pulls 9.x); drop it once Jest/Stryker's own ranges reach 11. Mutation is scoped to exactly the functions `tests/unit/*.test.js` imports (not whole files): the pure, DOM-free `calculatePaymentPlan`/`formatDate`/`calculateMonthsBetweenDates` in `debtCalculator.js`, `utils.js`'s tested formatting/sanitizing helpers, the record-shape sanitizers in `sanitizers.js`, the tested `retirementCalculator.js` functions, the pure `settings.js` helpers (#548), and all of `balanceHistoryCore.js`, `mergeDedupe.js`, `passwordPolicy.js`, `planSettingsPatch.js`, `concurrency.js`, `ledgerKeyRemap.js`, `recordVersions.js`, `refreshPolicy.js`, `resourceDeletion.js`, `projectionCache.js`, `recurringOccurrences.js`, `ledgerStateCore.js`, `netWorthCore.js`, `notificationsCore.js` and `undoCore.js`, plus the tested `projectionCore.js` functions. Feature modules taking `app`/DOM state are out of scope.

**Per-file floors and PR runs (#549).** Stryker's thresholds are global, so `tools/mutationFloors.cjs` checks each file in `reports/mutation/mutation.json` (the `json` reporter) against `tools/mutationFloors.json` and fails on a file below its floor or a mutated file with no floor. Floors are `floor(score) - 3` from a full run (`node tools/mutationFloors.cjs --derive`); re-derive them when tests raise a score, and never lower one silently. **Derive from a CI report** (the `mutation-report`/`mutation-report-pr` artifact's `mutation.json`), not a local run: a slower machine times out more mutants, Stryker counts a timeout as detected, and a local run once put `recurringOccurrences.js` 5 points above what CI measures. On main, `mutation-testing` runs `stryker run --incremental --force` and caches `reports/stryker-incremental.json`; on a PR, `mutation-testing-pr` restores that baseline and runs `--incremental` plus the floors, but only when the PR touches a scoped file (`node tools/strykerScope.mjs --files`), `tests/unit/`, or the mutation/Jest config. A new scoped file needs a floor. `strykerScope.test.js` also fails when an exported `sanitize*`/`isValid*`/`remap*` in `sanitizers.js` is neither scoped nor excluded (#548).

**Scope is by function name, not line number (issue #452).** `MUTATE_SCOPE` in `tools/strykerScope.mjs` lists names per file. `stryker.config.mjs` calls its `buildMutateGlobs()`, which parses each file with Babel at config-load time and emits exact `file:start-end` ranges. Hand-written ranges had drifted until most pointed at unrelated code. To change the scope, edit `MUTATE_SCOPE`, or add a function to `EXCLUDED` with a reason; never write line numbers. `tests/unit/strykerScope.test.js` (runs on PRs, unlike `mutation-testing`) fails when a name doesn't resolve to exactly one declaration, or when a unit test imports a function from a scoped file that is in neither list. `node tools/strykerScope.mjs` prints the resolved globs. See `docs/superpowers/specs/2026-08-02-stryker-js-mutation-testing-design.md`.
